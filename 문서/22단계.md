# 22단계 — 7B 전체: 머리 128 의 어텐션까지 글(geul) 언어로 (2026-10-11)

21단계는 7B(Qwen2.5-7B-Instruct Q8_0)의 행렬곱만 쟀다. 결과는 프롬프트 2048 에서 r 1.20, 8192 에서 r 1.77 이었다. 이 단계는 7B 를 통째로
돌린다. 사용자 결정(2026-10-11): "행렬곱 먼저, 그다음 전체" — 그 "전체"가 이 단계다.

7B 의 머리 크기는 128 이다(0.5B 는 64). 그래서 어텐션의 계약과 커널을 넓혀야 한다. 판정 기준을 결과보다 먼저 적는다.

## 계약을 넓힌다 — 머리 크기 128 (문서/계약.md 에 더한다)

0.5B(머리 64)의 계약은 바뀌지 않는다. 머리 128 에서 다른 것은 셋이다.

1. **점수의 눈금.**
   - 머리 64 는 × 0.125 로, 2 의 거듭제곱이라 정확하다.
   - 머리 128 의 1/√128 은 2 의 거듭제곱이 아니다. 그래서 상수 c = 짧은실수(1/√128) = 0.088388346…(가까운 반올림)을 정하고 s ← s × c 를
     **곱 한 번(반올림 하나)**으로 적는다.
   - 그 앞의 점수 합은 32 칸 블록 넷을 b 오름차순으로 곱해더하기 사슬로 잇는다(블록 0 이 처음 값 — 머리 64 의 둘과 같은 꼴).
2. **RoPE.** 표 cos · sin 은 [위치][64] 다. θ_i = θ^(−2i/128)(i = 0 … 63)을 fp64 로 바르게 하고, 각 = 위치 · θ_i(fp64 곱), cos · sin 은
   짧은실수로 바르게 반올림한다. 돌리는 짝은 (i, i + 64)이다. 곱해더하기의 꼴은 머리 64 와 같다.
3. **출력 o_d** 는 값의 32 칸 블록 넷(d 0 … 127)마다 머리 64 와 같은 식이다. 적힌지수 · 합 l · 접기(두 층)는 그대로다.

## 무엇을 만드나

- **CPU 참조**(`계약/정수계약.py`)를 머리 크기에 따라 넓힌다(머리 64 의 값은 그대로).
  - 7B 의 앞으로(정수 계약)는 시간이 들기 때문에, 정수 블록의 합을 짧은실수 BLAS 로 셈한다. 블록 하나의 합이 2¹⁹ 아래라 순서와 상관없이
    정확하다.
  - 이 빠른 판이 `정수계약.행렬곱` 과 비트까지 같은지는 따로 시험한다.
- **커널 생성기**(글 — `커널/생성*.gl`)에 모델의 크기를 매개변수로 넣는다.
  - 7B 모듈 `qwen2Q8_7b.gl` 을 낸다. 0.5B 모듈은 바이트까지 그대로 둔다(19a 를 다시 본다).
  - 7B 모듈의 커널:
    - 정수 타일 판(끝손질 없음 · 잔차 · SwiGLU — K · N 은 띄울 때 받는다)
    - 줄 판(행 넷까지)
    - RMS 정규화
    - 임베딩
    - RoPE + KV(머리 128)
    - 프롬프트 어텐션(묶음 판 + 묶음 접기 — 머리 128, 새로)
    - 생성 어텐션(조각 + 조각 접기 — 머리 128)
    - SwiGLU 줄
    - 로짓 · 가장 큰 번호
- **호스트**(글)를 7B 크기로 넓힌다.
  - 프롬프트는 1024 행 이하의 덩이로 넣는다. 계약상 비트가 같다(20a). 21단계의 L2 틈도 이것으로 피한다.
  - 생성은 토큰마다 CUDA 그래프로 돌린다(7B 에는 생성 메가커널을 아직 만들지 않는다).
  - 실행기가 7B GGUF 를 받는다.

### 미리 밝혀 둘 것

1. **계약을 넓힌다(위).** 머리 128 의 점수 눈금은 반올림 하나를 더한다. 머리 64 는 그대로다.
2. **QKV 는 끝손질 없는 타일 판에 RoPE + KV 커널을 따로 잇는다.** 0.5B 의 QKV 타일 끝손질(RoPE · KV 를 타일 안에서)은 머리 64 에 묶여 있다.
   따로 잇는 길은 활성값을 한 번 더 쓰고 읽는다.
3. **프롬프트는 1024 행 이하의 덩이로 넣는다.** 어텐션은 묶음 판 하나만 쓰고, 행렬곱은 L2 에 드는 크기로 간다.
4. **생성은 토큰마다 그래프다.** 0.5B 의 생성 메가커널(15단계)은 크기에 맞춰 짜여 있어 7B 에는 아직 없다.
5. **머리 128 의 어텐션 커널은 새로 짠 첫 판이다.** 0.5B 커널처럼 바닥까지 다듬지 않았다. 속도는 그대로 적는다.
6. **최대 문맥은 8192 다.** 12 GB 에 7B Q8_0(8.1 GB)과 정수 KV 캐시를 둔다.
7. **대조 도구는 파이썬이다**(CPU 참조 · 견주기). 엔진과 실행기는 글이다.

### 밝혀 둘 것

1. **첫 판은 미리 적은 모듈 목록에서 벗어났었다.** 첫 판(0399de4)은 "줄 판(행 넷까지)" · "생성 어텐션(조각 + 조각 접기 — 머리 128)" 없이 생성을
   타일 판 · 묶음 어텐션의 행 하나로 돌렸다. 비트는 맞았지만 느려서(문맥 2048 에서 26.4 ms/토큰, 띄움마다 이벤트를 끼운 값) 미리 적은 대로 두 판을
   만들었다(d98c6dd). 판정은 d98c6dd 의 공식 실행으로 했고, 첫 판의 시운전 결과(22a · 22b 와 같은 시험이 모두 맞음)는 기록으로만 둔다.
2. **상태 한 칸의 크기를 잘못 적었었다.** 머리 128 의 묶음 · 조각 상태(M, L, 빈 둘, O 128 = 132 칸)를 생성기에 `4 · 128 + 4 = 516` 으로 적었다.
   쓰는 판과 읽는 판 · 엔진 · 시험이 모두 같은 값을 써서 값은 맞았지만 묶음칸이 4 배(7B · 문맥 8192 에서 약 470 MB)였다. 공식 실행 전에 132 로
   고쳤다(d98c6dd).
3. **줄 판의 생성 코드에서 이름이 겹쳤었다.** 쌍 변수 `b{i}` · `p{i}` 의 i = 0 이 고리 변수 `b0` · `p0` 과 같은 이름이 되어 안쪽 선언이 바깥을
   가렸다(글은 안쪽 블록의 같은 이름을 허락한다 — 14단계에서도 본 꼴). 줄 판 시험의 첫 실행이 잘못된 주소 접근(오류 700)으로 멈춰 찾았고,
   고리 변수 이름을 바꿨다.
4. **줄 판의 속도 시도 셋은 효과가 없었다**(커널마다의 시간 — 띄움마다 이벤트): 열 32 → 16(블록 두 배) 19.08 → 19.25 ms, 사슬을 여덟씩 펼침
   19.12 ms, 스레드마다 미리 읽는 쌍 4 → 8 19.15 ms. 펼친 사슬은 남겨 두었다(값과 시간이 같다). 효과가 있던 것: 조각 접기의 배율을 스레드들이
   나눠 셈함 — 문맥 8192 에서 접기 0.85 → 0.38 ms.
5. **실행기의 올림 차례를 바꿨다.** PTX 가 모델마다 달라, GGUF 를 열고 설정을 읽은 뒤에 쿠다 일꾼을 띄운다(예전에는 쿠다 일꾼이 먼저). 0.5B 의
   '올림'은 18단계 기록 안이다(위의 기록 — 236 ~ 265 ms).
6. **7B 의 판 고르기는 로짓 판(행 하나)도 미리 고른다**(끝 로짓이 타일 판이라). 판 고르기는 7B 에서 약 3.6 초 — 실행기는 이것을 뒤에서 하고 첫 질문
   전에 기다린다.
7. **속도 도구는 최대길이 8448** 로 엔진을 만든다(문맥 8192 뒤에 65 토큰을 생성할 자리). 미리 적은 최대 문맥(8192)과 같은 생성 길이다.
8. **대조 도구는 파이썬이다**(미리 적은 대로): CPU 참조, 커널 시험의 드라이버(ctypes), 입력 토큰(7B GGUF 의 토크나이저 — 엔진/토크나이저.py).
   엔진 · 실행기 · 시험 도구의 글 쪽(시험_7B · 재기_7B)은 글이다.
9. **공식 스크립트의 실수 둘.** 0.5B 회귀(18d)의 기록 줄에 bash 의 한글 변수 이름을 써서 결과 글이 비었다(대입이 명령으로 읽힌다 — 20단계에
   이어 두 번째). 오류 글로 보면 '같다' 쪽이 실행됐고, cmp 로 다시 견줘 18단계 기록과 파일째 같음을 확인했다(기록 파일에 바로잡은 줄).
   22c 의 첫 시도는 Windows PowerShell 5.1 이 BOM 없는 스크립트를 cp949 로 읽어 구문 오류로 시작도 못 했다(실행기는 돌지 않았다). BOM 을 붙여
   다시 돌렸다.
10. **생성의 "같다" 칸은 0.004 차로 넘었다**(문맥이 짧을 때 r = 1.054, 기준 1.05). 미리 적은 칸 그대로 "느리다"로 적는다.

### 글(geul) 언어에서 본 것

- **모양마다 생성기 함수를 새로 쓸 일은 머리 크기에 묶인 판뿐이었다.** 타일 판 · RMS · 임베딩 · 가장 큰 번호 · 정수로는 0.5B 와 같은 글 생성
  함수에 설정만 바꿔 넣었다. 새로 쓴 것은 머리 128 의 판(생성머리128.gl 508 줄)과 생성 길의 판(생성줄128.gl 341 줄)이다. 생성기가 글이 된
  19단계의 덕을 이번에 처음 봤다 — 0.5B 의 소스는 바이트 하나 바뀌지 않았다(19a 를 다시 확인).
- **안쪽 블록의 같은 이름이 또 일을 냈다.** 생성기가 만든 줄 판에서 쌍 변수 `b0` · `p0` 이 같은 이름의 고리 변수를 가렸다(14단계의 `적힌지수식`
  과 같은 꼴). 비트 시험이 잡았지만, 글이 안쪽 블록의 같은 이름을 막으면(v0 규칙 후보) 컴파일 때 잡혔을 것이다.
- **칸 판(위치를 장치의 걸음칸에서 읽는 판)이 7B 의 생성을 쉽게 했다.** 위치가 매개변수가 아니라 장치 메모리에 있어, 토큰마다의 그래프를 한 번
  지어 고치지 않고 되풀이한다 — 0.5B 의 생성 메가커널(15단계) 없이도 띄움 비용이 작다.
- 공식 실행 스크립트(bash)에 한글 변수 이름을 썼다가 대입이 명령으로 읽혔다(20단계에 이어 두 번째). Windows PowerShell 5.1 은 BOM 없는
  UTF-8 스크립트를 cp949 로 읽는다. 둘 다 글 언어가 아니라 도구의 일이다.

### 남은 것

- **생성의 남은 거리**(llama.cpp 대비 1.05 ~ 1.07 배): 줄 판의 효율(qkv · o · down 이 대역폭의 75~90% — 블록 수가 적은 행렬곱일수록 낮다),
  RMS 의 띄움(층마다 둘, 토큰당 약 0.4 ms), 긴 문맥의 조각 어텐션(문맥 8192 에서 1.7 ms — 블록 하나에서 워프 하나만 셈한다).
- **채팅의 끝 토큰 뒤 걸음**: 생성 그래프는 끝 토큰을 장치에서 알아채지 못해, 실행기가 걸음 묶음(1 · 2 · 4 · 8 · 16)을 띄운 뒤에 가린다. 답마다
  많게는 15 걸음(약 0.26 초)이 버려진다 — 실행기가 보이는 초당 토큰(36 ~ 50)이 재기(57)보다 낮은 까닭. 7B 의 가장 큰 번호 판이 끝 토큰에서 걸음칸에
  멈춤 표시를 쓰고 판들이 그것을 보게 하면 된다(0.5B 의 생성기 함수는 바꾸지 않는다 — 19a).
- **프롬프트**: 행렬곱은 21단계 그대로(2048 에서 r 1.2 급), 머리 128 의 묶음 어텐션은 첫 판이다(레지스터 255 · 넘침 384 B — 8192 에서 프롬프트의
  28%). 계약의 어텐션은 자리 둘 × 자리 둘이라 텐서 일이 네 배다 — 그 일을 int8 최고치로 셈한 바닥(8192 에서 168 ms)의 2.9 배에 있다.
- 실행기의 판 고르기가 7B 에서 약 3.6 초(첫 질문 전에 기다린다) — 고른 판을 파일에 두면 없앨 수 있다.
