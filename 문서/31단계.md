# 31단계 — Vulkan 경로: AMD 그래픽카드에서 GeulPU

## 목표
AMD 그래픽카드에서 GeulPU 를 돌린다. 지금 GeulPU 는 PTX(NVIDIA)만 낸다. Vulkan(SPIR-V)은 NVIDIA · AMD · 인텔의 드라이버가 모두 받고,
드라이버에 들어 있는 `vulkan-1.dll` 만으로 쓸 수 있다 — 툴킷 없이 드라이버만으로 도는 지금의 PTX 경로와 같은 자리다.

1. 사전 측정 — 같은 NVIDIA 카드에서 Vulkan 이라는 통로가 얼마를 잃는가(llama.cpp 의 CUDA 대 Vulkan).
2. 탐침(이 문서의 판정) — 계약의 핵심 계산이 Vulkan 에서도 CPU 참조와 비트까지 같은가, 드라이버마다 무엇을 보장하는가.
3. 그 뒤 — 글(geul) 컴파일러의 SPIR-V 뒷단, AMD 카드에서의 속도(같은 급 NVIDIA 대비) · 같은 비트 확인.

## Vulkan 이 계약과 어긋날 수 있는 곳 (사양에서 읽은 것)
- **곱하고 더하기(FMA)**: 계약은 블록 사이를 `fma.rn`(반올림 한 번)으로 잇는다. Vulkan 의 `GLSL.std.450 Fma` 는 합친 연산을 보장하지
  않는다(곱하고 더하기를 따로 반올림해도 된다). 보장하는 것은 새 확장 `VK_KHR_shader_fma` 의 `OpFmaKHR` — 드라이버가 지원해야 한다.
- **비정규수**: 아주 작은 수를 0 으로 버리는지 지키는지(float controls)가 기기마다 다르다.
- **워프 크기**: AMD 는 32 또는 64.
- **행렬 명령**: cooperative matrix 의 정수(int8) 모양이 기기마다 다르다(없는 기기도 있다).
- **메모리**: 위의 사전 측정처럼 윈도에서 VRAM 이 넘치면 조용히 느려진다.

## 탐침 — 판정 기준 (실행 전에 적음)
탐침은 파이썬 + ctypes 로 `vulkan-1.dll` 을 직접 부르고, SPIR-V 는 손으로 짠 작은 조립기로 만든다(다운로드 없음). 연구용 탐침이고,
뒷단은 글 컴파일러에 만든다. 커널은 계약의 Q8_0 행렬곱 한 칸이다: 32 값 블록마다 자리 둘의 정확한 정수 합 S₁ · S₀ →
T = 256·S₁ + S₀ → u = 실수(T)(정확) → y ← fma(u, P·d, y) 를 블록 차례대로. CPU 기준은 유리수로 정확히 계산해 짧은실수로 한 번만
반올림한다(합친 FMA 의 정의 그대로).

- **31a — NVIDIA (RTX 4070 Ti) 의 Vulkan**: 무작위 4096 칸 이상과 경계 시험(비정규수가 나오는 작은 척도 · 큰 지수)이 CPU 기준과 모두
  비트까지 같다 — FMA 를 `GLSL.std.450 Fma` 또는 `OpFmaKHR` 로. 대조군으로 곱하기 · 더하기를 따로 한 판(합치기 금지)은 CPU 기준과
  달라야 한다(시험이 FMA 의 차이를 잡는다는 증거).
- **31b — 다른 회사의 드라이버 (이 PC 의 Intel UHD 770 내장 그래픽)**: 같은 시험이 비트까지 같으면 통과. 다르면 어느 연산(FMA ·
  비정규수)에서 갈리는지 밝히고, 계약이나 뒷단에서 고칠 자리를 적는다.
- **31c — 능력 표**: 두 기기의 Vulkan 판, `VK_KHR_shader_fma`, float controls(비정규수 보존 · 반올림 방식), cooperative matrix 의 정수 모양,
  정수 내적 가속, 서브그룹 크기를 적는다. AMD 카드에서 같은 탐침을 돌릴 때의 대조표가 된다.

## 결과 — 탐침 (2026-10-13)
탐침: [`탐침/vulkan/`](../탐침/vulkan/) — `spv.py`(SPIR-V 조립기) · `vk.py`(`vulkan-1.dll` 호출) · `탐침31.py`. 시험은 네 묶음이다.

- 큰지수.

CPU 기준은 넷이다(합친 FMA · 따로 한 곱 · 더하기, 그리고 둘 각각의 비정규수 버림판). 기준끼리도 시험이 갈리는지 먼저 봤다. 합친 FMA 와

두 장치의 출력끼리도 비트까지 같다(출력 해시). 무작위 · 큰T · 큰지수의 합친 FMA 판과 따로 판, 비정규수 묶음의 FMA 판이 그렇다.
비정규수 묶음에서 버림 기준과 어긋난 두 칸은 두 장치가 모두 −0 을 냈는데 탐침의 기준이 +0 을 냈다. 버림이 어느 자리에서 일어나는지를
기준이 장치와 다르게 잡은 것이다.

**판정**
- **31a — 못 미침.** 비정규수가 없는 시험은 모두 비트까지 같고 대조군은 달랐다. 그러나 비정규수 묶음에서 47 칸이 다르다. NVIDIA 의
  Vulkan 드라이버는 비정규수를 0 으로 버리고, 보존을 요청할 수 없다(`shaderDenormPreserveFloat32` 없음). `OpFmaKHR` 판은 돌리지 않았다.
  GLSL `Fma` 가 이미 합친 연산이었고, 비정규수는 FMA 의 문제가 아니다.
- **31b — 통과.** Intel 내장 그래픽은 비정규수 보존 모드(DenormPreserve)를 켜면 네 묶음 모두 CPU 기준과 비트까지 같다.
- **31c** — 위 표.

**뜻**
- 계약의 세 셈(정수 합, 정수 → 실수 반올림, 합친 FMA)은 Vulkan 에서 두 회사(NVIDIA · Intel)가 CPU 기준과 비트까지 같다. 회사가 다른
  GPU 끼리 같은 비트를 낸 것을 처음 확인했다.
- 막히는 곳은 비정규수 하나다. 지금 계약은 비정규수를 보존하는데(CUDA · CPU), NVIDIA 의 Vulkan 은 버린다. 길은 둘이다.
  - (가) 계약을 '비정규수는 부호를 지켜 0 으로' 로 고친다. 모든 경로(CUDA · CPU · Vulkan)가 장치의 버림 모드에 기대지 않고 그 규칙을
    코드로 따른다.
  - (나) 계약의 값 범위를 정해 비정규수가 생기지 않게 한다.

  실제 모델 계산에서 비정규수가 나오는 일은 드물다(적힌지수는 이미 정규수 밖을 0 으로 둔다). 그래도 '어디서나 같은 비트' 는 드문 경우까지
  덮어야 한다.
- NVIDIA 의 Vulkan 에는 PTX 의 m16n8k32 와 같은 모양의 정수 행렬 명령(16×8×32)이 있다. Vulkan 경로도 정수 텐서 코어를 쓸 수 있다.
  Intel 내장 그래픽에는 정수 내적(4 × 8 비트)만 있다.
- AMD 는 아직이다. 같은 탐침을 AMD 카드에서 돌려 비정규수 보존을 지원하는지, cooperative matrix 의 모양, 서브그룹 32 / 64 를 봐야 한다.

## 탐침 둘 — 셈 규칙 (판정 기준, 실행 전에 적음)
첫 탐침에서 막힌 비정규수에 더해, 사양을 다시 읽다 찾은 것이 있다. Vulkan 은 나눗셈(`OpFDiv`)의 정확도를 2.5 ULP 로만 요구하고,
제곱근도 정확한 반올림을 요구하지 않는다. 계약은 RMSNorm · SwiGLU 에서 정확한 반올림의 나눗셈 · 제곱근(`div.rn` · `sqrt.rn`)을 쓴다.
연산 하나씩(곱 · 더하기 · FMA · 나눗셈 · 제곱근 · 짝수로 반올림)을 경계값과 무작위 값으로 돌린다. 장치는 NVIDIA 의 Vulkan(기본),
Intel 의 Vulkan(기본 · 보존 모드 · 버림 모드), CUDA PTX(`.ftz` 없음 · 있음)다. CPU 기준은 유리수로 정확히 계산한 뒤 버림 규칙의 후보별로 낸다.
후보는 셋으로 가른다: 판단을 반올림 앞에서 하는가 뒤에서 하는가, 비정규수 입력도 0 으로 보는가, 0 의 부호를 지키는가.

- **31d — 비정규수 규칙**: 버림이 일어나는 장치들(NVIDIA Vulkan 기본, PTX `.ftz`, Intel 버림 모드)의 결과를 **모두** 설명하는 버림 규칙
  하나를 찾는다. 경계값은 다섯이다.
  - 반올림하면 막 정규수(2⁻¹²⁶)가 되는 값
  - 비정규수로 떨어지는 값
  - 비정규수 입력
  - FMA 안의 곱만 비정규수인 경우
  - 반실수(f16) 비정규수를 짧은실수로 읽기(Q8_0 의 척도 d 는 반실수 비정규수일 수 있다 — CUDA 의 `cvt.f32.f16` 은 정확)

  FMA 가 정말 합쳐지는지(곱을 반올림하지 않는지)도 같은 자료로 가린다 — 곱이 정확히 반올림의 한가운데일 때 아주 작은 c 를 더해 본다.
  Vulkan 은 `SignedZeroInfNanPreserve` 가 없으면 0 의 부호를 무시하는 최적화를 허락하므로, 되는 장치는 그 모드로도 한 번 더 돌린다.

  찾으면 그 규칙을 계약에 넣는 안을 낸다. 고칠지는 사용자가 정한다. 하나로 설명되지 않으면 장치마다 다른 자리를 적는다.
- **31e — 나눗셈 · 제곱근 · 짝수 반올림**: 각 장치의 Vulkan `OpFDiv` · GLSL `Sqrt` · `RoundEven` 이 정확한 반올림 기준과 무작위 10 만 개 +
  경계값에서 모두 같은지 본다. 다르면 Vulkan 뒷단은 FMA 로 정확한 반올림을 짜야 한다(계약은 그대로).

### 31d — 버림 규칙 하나를 찾음
버림이 일어나는 네 길이 **같은 규칙 하나(아래 R)** 로 모두 설명된다.
- NVIDIA Vulkan 의 기본 동작(고를 수 없음)
- Intel Vulkan 의 기본 동작(기본이 이미 버림)
- Intel Vulkan 의 버림 모드
- CUDA PTX `.ftz`

`SignedZeroInfNanPreserve` 를 켜도 결과는 같았다.

| CUDA PTX (지금 GeulPU 의 길) | IEEE | IEEE | IEEE | IEEE | IEEE |
| CUDA PTX `.ftz` | R | R | R | R | R |

규칙의 각 부분은 아래 자료가 갈랐다.
- **판단 위치 — 반올림 뒤, 지수 제한 없이.**
  - 곱: `막정규수로올림` 182 칸과 `비정규수칸가운데` 56 칸이 갈랐다. 정확한 곱이 2⁻¹²⁶ 바로 아래이고, 반올림하면 2⁻¹²⁶ 이 되는 값이다.
  - FMA: `상쇄로막정규수근처` 400 칸이 갈랐다.
  - 더하기는 이 판단을 가를 수 없다. 정규수 둘의 합이 비정규수 범위에 오면 늘 정확해서 반올림이 일어나지 않는다.
  - 나눗셈도 2⁻¹²⁶(1 − j·2⁻²⁴) 꼴 말고는 그 띠에 몫이 올 수 없다. 그 꼴에서 PTX `.ftz` 와 Vulkan 이 R 과 같은 쪽으로 갔다.
- **입력** — 비정규수 입력은 0 이다. 0 의 부호는 지킨다.
- **FMA 합침** — `동점깨기` 720 칸이 갈랐다. 곱이 정확히 반올림의 한가운데일 때 c 를 아주 작게 둔 경우다.
  - '곱을 따로 반올림' 후보는 모두 떨어졌다.
  - c 를 아주 작은 정규수로 둔 대조군이 합침을 확인했다.
  - c 를 비정규수로 둔 칸은 '입력 버림'을 확인했다.
- **반실수 읽기** — `UnpackHalf2x16` 은 모든 반실수 63,490 개(비정규수 2,046 개 포함)에서 정확했다. 두 장치, 모든 모드에서 같았다.

### 31e — Vulkan 의 나눗셈 · 제곱근은 바른 반올림이 아님
바른 반올림과 다른 칸의 수다(ULP 차). Intel 은 네 모드가 모두 같았다.

| 칸 | NVIDIA Vulkan | Intel Vulkan | CUDA `div.rn` · `sqrt.rn` (`.ftz` 있음 · 없음) |
|---|---|---|---|
| 나눗셈 무작위 80,000 | 23,594 (1 ULP 23,520 · 2 ULP 74) | 23,190 (1 ULP 23,136 · 2 ULP 54) | 0 |
| 나눗셈 한가운데 근처 20,000 | 10,173 | 10,129 | 0 |
| 나눗셈 계약 모양 10,000 (RMSNorm 평균 · SwiGLU · O/L) | 2,944 | 3,002 | 0 |
| 제곱근 무작위 80,000 | 13,319 (모두 1 ULP) | 6,376 (모두 1 ULP) | 0 |
| 제곱근 한가운데 근처 20,000 | 9,804 | 9,490 | 0 |
| 제곱근 계약 모양 10,000 | 1,697 | 811 | 0 |
| 짝수 반올림 100,000 | 0 | 0 | 0 |
| 반실수 읽기 63,490 | 0 | 0 | 0 |

'한가운데 근처'는 몫 · 제곱근이 짧은실수 두 수의 한가운데에서 2⁻⁴⁸ 쯤만 벗어나게 만든 값이다. 바른 반올림을 가리는 가장 어려운 칸이다.

### 판정
- **31d — 찾음.** 측정한 버림의 길 넷이 R 하나로 모두 설명된다. AMD 는 아직 재지 않았다. 같은 탐침을 AMD 기기에서 돌려야 한다.
- **31e — 나눗셈 · 제곱근은 못 미침, 짝수 반올림 · 반실수 읽기는 통과.** Vulkan 에서 정확한 나눗셈 · 제곱근이 필요하면 FMA 로 직접 짜야
  한다. 두 회사 모두 해당된다. 계약은 바꿀 필요가 없다.

### 뜻 — 계약을 R 로 바꾸는 안 (결정은 사용자)
- **왜 R 인가**
  - NVIDIA Vulkan 은 비정규수를 지키지 못한다. 그래서 지금 계약(IEEE, 비정규수 보존)으로는 NVIDIA 를 Vulkan 으로 돌릴 수 없다.
  - 버림은 모든 GPU 가 하는 공통분모이고, 잰 네 길이 비트 규칙까지 같다.
  - 속도 손해가 없다. `.ftz` 는 같은 명령이다.
- **고칠 것**
  - CUDA 커널: 짧은실수 연산마다 `.ftz` 를 붙인다(글(geul) 컴파일러의 PTX 뒷단).
  - CPU 기준(`계약/정수계약.py`): 연산마다 R 을 적용한다.
  - Vulkan: NVIDIA 는 기본 동작 그대로, 다른 회사는 `DenormFlushToZero` 를 선언한다.
- **실제 모델에서 비정규수가 나올 수 있는 자리** (손으로 따져 본 것)
  - 어텐션의 e · 2^(E_v − 13): 점수 차가 약 75 를 넘을 때다. 다음 자리 바꾸기에서 늘 0 이 되어 결과에 남지 않는다.
  - 접기의 O · 가: FMA 의 c 로 들어간다. 곱이 정확히 한가운데일 때만 마지막 비트를 가를 수 있다.
  - SwiGLU 의 s · u: 게이트가 약 −87 일 때다. 다음 자리 바꾸기에서 0 이 된다.
  - 거의 0 인 활성값 블록의 P · d.

  그래서 바꿔도 지금까지의 출력이 그대로일 가능성이 크다. 다만 따져 본 것이지 잰 것은 아니다.
- **확인할 것** — 고치기 전에 둘을 확인한다.
  1. `.ftz` 커널로 R1 32 문제를 다시 돌려, 기존 로짓 해시(82,673 걸음)와 같은지 본다. 같으면 지금까지의 결과(세 세대 교차검증 포함)가
     그대로 유효하다. 이 PC 의 GPU 를 쓰는 실행이다.
  2. AMD 에서 이 탐침을 돌려, AMD 의 버림 모드가 R 과 같은지 본다.
- **다른 안** — 계약을 그대로(보존) 둔다.
  - Vulkan 은 보존 모드가 되는 장치(Intel, AMD 는 미확인)만 지원하고, NVIDIA 는 CUDA 로만 돌린다.
  - 계약과 결과를 다시 확인할 일은 없다.
  - 대신 NVIDIA 와 AMD 를 같은 Vulkan 코드로 견줄 때, NVIDIA 쪽은 계약 밖이 된다.
