# 23단계 — 4비트(Q4_0)를 계약 안에, 7B 생성의 고정 비용 (2026-10-11)

사용자 방향(2026-10-11): 로컬 AI 를 실제로 쓰는 사람들은 VRAM 50 ~ 100 GB 의 작은 서버급, 그리고 대형 서버에서 12B · 30B · 120B 를
돌린다. 7B 와 4비트에서부터 무너지면 그 위에서는 더 무너진다. 추천 순서대로 간다: (1) 생성의 고정 비용과 Q4_0, (2) 설정에서 모델 모양
만들기(14B · 32B · 72B), (3) 층 나누기 다중 GPU, (4) k-양자화 · MoE · 서버 기능. **시험은 이 PC(RTX 4070 Ti 12 GB 한 장) 안에서만** 한다.

이 단계가 (1)이다. 판정 기준을 결과보다 먼저 적는다.

## 왜 둘을 함께 하나

22단계의 7B 생성(Q8_0)에서 행렬곱이 아닌 일(RMS · RoPE + KV · 어텐션 · 접기 · 띄움 사이)이 토큰당 약 1.3 ~ 1.8 ms 였다. 행렬곱(가중치 7.5 GB
읽기)은 17 ms 남짓이라 그 몫은 10% 안팎이다. 4비트에서는 읽는 바이트가 절반 남짓이라 같은 고정 비용이 두 배의 몫이 된다. 그래서 4비트를
제대로 하려면 고정 비용을 먼저(또는 함께) 줄여야 한다.

## 무엇을 만드나

1. **Q4_0 을 글 생성기 · 호스트에.** 계약(문서/계약.md 1절)은 이미 Q4_0 을 포함한다: q = 니블 − 8, 블록 척도 d(반실수), S_j = Σ D_j · q
   (정확), 나머지는 Q8_0 과 같다. 8단계(GPT-2)에서 파이썬 생성기로 검증한 판(타일 판의 Q4_0 B 읽기 · 줄 판의 Q4_0 dp4a)을 글 생성기로
   옮기고, 7B 의 판(줄 판 · 로짓 · 임베딩)에 Q4_0 을 더한다. 모듈은 `qwen2Q4_7b`. 호스트는 GGUF 의 Q4_0 텐서를 엔진의 배치로 깔고,
   실행기는 모양과 형식에 맞는 PTX 를 고른다.
2. **Q4_0 파일은 이 PC 에서 만든다.** 공식 q4_0 GGUF 는 llama.cpp 의 규칙대로 출력 가중치를 Q6_K(k-양자화 — (4)에서)로 둔다. 그래서 가진
   7B Q8_0 에서 `llama-quantize --allow-requantize --pure` 로 모든 텐서를 Q4_0 으로 만든다. 글과 llama.cpp 가 같은 파일을 쓴다.
3. **7B 생성의 고정 비용.** 행렬곱이 아닌 일을 줄이거나 가중치 읽기와 겹친다. 방법은 재서 고른다(후보: 다음 가중치를 L2 에 미리 올리기,
   RMS 를 앞 행렬곱의 마지막 블록에, RoPE + KV 를 qkv 의 끝손질에, 접기를 마지막 조각 블록에, 7B 의 생성 메가커널). 무엇을 하든 값은
   그대로여야 한다(23b).

### 미리 밝혀 둘 것

1. **Q4_0 파일은 이 PC 에서 Q8_0 을 다시 양자화해 만든다**(공식 q4_0 이 아니다 — 공식 파일은 출력 가중치가 Q6_K). 값이 F16 에서 바로 만든
   것과 조금 다르지만, 두 엔진이 같은 파일을 쓰므로 견주기는 공정하다. 정확도는 이 단계의 판정이 아니다.
2. **고정 비용을 줄이는 방법은 재서 고른다.** 판정은 방법과 상관없다. 시도한 것과 안 된 것은 모두 적는다.
3. **이 PC 에서만 잰다.** 14B 는 (2) 모양 일반화 뒤에(24단계 — 14B Q4_0 은 약 8.5 GB 라 이 PC 에 든다).
4. **대조 도구는 파이썬이다**(CPU 참조 · 견주기). 엔진 · 생성기 · 실행기는 글이다.

### 고정 비용 — 무엇을 했고 얼마나 줄었나

미리 적은 후보 가운데 하나(다음 가중치를 L2 에)만 해 보고 걷었다. 재서 고른 넷이 남았다 — 모두 계약의 식과 차례를 그대로 둔다(판이 계산을
나누는 꼴만 바꾼다). 시운전의 생성 시간(ms/토큰, `재기_7B` 한 프로세스씩, Q4_0):

Q8_0 은 22단계 17.672 · 18.110 · 19.112 → 정수줄하나 16.894 · 17.319 · 18.302 → 어텐션 넷 16.572 · 16.861 · 17.880 → 공식 16.503 · 16.743 · 17.634.

1. **줄 판(정수줄하나)** — Nsight Compute 로 본 22단계의 줄 판(정수줄자리)은 블록이 SM 마다 둘(레지스터 96 · 공유 44 KB — 점유 33%)이고,
   한 바퀴(블록 64 개) 안에서 읽기 → 셈 → 장벽 → 워프 하나의 사슬 → 장벽을 차례로 해서 읽기가 쉬는 동안이 길었다. 그래서 그래프 안에서는
   따로 띄울 때보다 훨씬 느렸다(Q4_0 down: 따로 85.9 µs · 그래프 안 약 110 µs, DRAM 69%). 새 판은 스레드 128 · 판(블록 8 개 × 열 32) 넷의
   비동기 복사 고리다 — 판 s 를 기다린 뒤 판 s + 3 의 복사를 먼저 띄우고, 스레드마다 같은 블록의 열 둘(SwiGLU 넷)의 u 와 척도를 짝판에,
   열의 스레드가 판 s − 1 의 사슬을 잇는다. Q4_0 은 니블(q + 8, 0 … 15 — 부호 있는 바이트로도 같은 값)을 그대로 dp4a 하고 8 · ΣD 를 뺀다
   (정수라 S 가 같다 — 니블을 부호로 바꾸는 명령이 빠진다). 첫 판은 마법수 M_0 을 전역에서 읽어 판마다 그 지연이 사슬에 걸렸다(down 93.7 µs
   — 옛 판보다 느림). M_0 도 4 바이트 비동기 복사로 판에 올리자 따로 띄울 때 qkv 26.4 → 22.3 · o 19.2 → 17.9 · down 85.9 → 83.0 µs(Q8_0 down
   171.6 → 154.2)가 됐고, 그래프 안의 down 이 따로 띄울 때와 같아졌다.
2. **L2 에 미리 읽기 — 걷었다.** 조각 어텐션의 블록이 일을 마친 뒤 다음 o 판의 가중치 층(Q4_0 7.2 MB)을 `prefetch.global.L2` 로 읽게 했다.
   o 는 빨라졌지만(띄움마다 이벤트로 2048: 0.559 → 0.396 ms) 어텐션이 그보다 더 느려졌다(0.963 → 1.156 ms — 미리 읽기가 커널의 끝을
   늦춘다). 생성 시간이 늘어 걷었다.
3. **조각 어텐션(정수조각어텐션넷)** — 생성(행 하나)에서 22단계의 조각 판은 가상 행 일곱(GQA 7:1)이 워프 하나에 들어가 워프 넷 가운데
   하나만 셈했다(짧은 문맥에서 Nsight Compute 로 커널 하나 17.9 µs — 명령 발행 슬롯 0.7%). 새 판은 점수 · 가림 · 지수를 워프 w 가 키
   [16w, 16w + 16) 에서, 가중합을 값의 블록 w 에서 한다. 행의 최댓값(정확 — 차례와 상관없다)과 정수 합 ml(정수)은 판으로 모으고, 지수는
   점수 뒤에 빈 키 판으로 나눈다.
4. **접기(정수조각접기넓)** — 두 층 접기의 묶음 안 접기(조각 16 개를 차례로)를 묶음마다 다른 스레드 128 이 나란히 하고(스레드 1024),
   묶음끼리의 접기는 스레드 128 이 차례로 한다. 식 · 차례는 22단계 판과 같다(8300 행에서 새 판 == 옛 판).
5. **RMS(RMS정규화정수줄펼침)** — 입력 · 감마를 먼저 다 읽고(스레드마다 14 개) 부분합을 같은 차례로 더한다. 22단계의 판은 고리 안에서
   읽고 더해 읽기의 지연이 겹치지 않았다(띄움마다 이벤트로 RMS 57 번 0.43 → 0.33 ms). 0.5B 모듈의 RMS 는 그대로 둔다(소스가 바이트까지
   같아야 한다).

### 밝혀 둘 것

1. **Q4_0 파일은 이 PC 에서 만들었다**(미리 적은 대로): 가진 7B Q8_0 에서 `llama-quantize --allow-requantize --pure … Q4_0` — 텐서 339 개 중
   Q4_0 198 · F32 141, 4,290,883,488 B. 글과 llama.cpp 가 같은 파일을 쓴다.
2. **새 판 넷은 미리 적은 판정 목록 밖이다.** 23a(1)에 적은 판(Q4_0 의 타일 · 줄 · 임베딩 · 로짓)에 더해, 생성 그래프의 새 판(정수줄하나 ·
   정수조각어텐션넷 · 정수조각접기넓 · RMS정규화정수줄펼침)도 같은 시험에 넣었다(공식 실행 전, 84c36b7). 23b 의 다섯 길과 23a(2)의 끝에서
   끝은 새 판으로 도는 생성 길을 함께 본다.
3. **시운전에서 잘못 잰 것 둘.** Q4_0 의 첫 커널마다 시간은 CPU 참조(11 분)가 도는 동안 재서 띄움 사이가 늘어났다 — 다시 쟀다. 커널 하나를
   따로 재는 일을 생성 그래프 재기와 같은 때 돌려 둘 다 흔들렸다 — 그래프 재기를 다시 했다. 위의 표는 다시 잰 값이다.
4. **23d 는 이 단계에서 손대지 않은 길이다.** 프롬프트 판(타일 · 묶음 어텐션)은 22단계 그대로이고 Q4_0 의 B 읽기만 더했다. 그래서 Q8_0 의
   프롬프트 r(1.145 · 1.299)은 22단계(1.140 · 1.296)와 같은 급이다.
5. **llama.cpp 의 값은 이 단계에서 다시 쟀다**(Q8_0 도 — 22d 의 값을 쓰지 않았다). Q8_0 생성은 16.80 · 17.08 · 17.82 ms 로 22d(16.76 · 17.10 ·
   17.87)와 0.3% 안이다.
6. **대조 도구는 파이썬이다**(미리 적은 대로): CPU 참조, 커널 시험의 드라이버(ctypes), 입력 토큰, 모음. 엔진 · 생성기 · 실행기 · 시험과 재기의
   글 쪽(시험_7B · 재기_7B · 재기_7B커널)은 글이다.
