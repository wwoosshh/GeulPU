# 19단계 — 커널 생성기를 글로: 빌드까지 글 컴파일러와 CUDA 드라이버만으로 (2026-10-11)

사용자 결정(18단계): "다른 언어의 종속없이 글컴파일러와 cuda dll만 통해서 작동하도록 구성해야해". 18단계 뒤 사용자의 물음(2026-10-11):
"이제 완전히 글, cuda 두가지로 진행가능해진거야?" — 답: 실행은 그렇다(실행기 = 글 실행 파일 + nvcuda.dll). 빌드는 아니다 — 실행기가 읽는 PTX 의
글 소스(`qwen2Q8.gl`, 6.8 MB)를 파이썬 생성기 `커널/커널생성.py` 가 만든다(그다음 PTX 로 옮기는 것은 글 PTX 뒷단 `자체PTX.exe`).

이 단계는 생성기를 글로 옮겨, 새로 받은 저장소에서도 **글 컴파일러가 빌드한 생성기 → 글 소스 → 글 PTX 뒷단 → PTX → 글 실행기 + nvcuda.dll**
로 파이썬 없이 채팅까지 가게 한다. 판정 기준을 결과보다 먼저 적는다.

## 할 것

- **글 생성기**(`커널/` 의 글 파일들) — `커널생성.qwen2_source()` 와 같은 소스를 낸다. 자체 호스팅 컴파일러(geul-lang-v2 `build/self_컴파일러.exe`)로
  빌드한다. 쓰는 법: `커널생성 qwen2Q8 <출력.gl>`.
- 옮기는 것은 `qwen2_source()` 가 지나는 길 — `sys.settrace` 로 세면 파이썬 2,395 줄 · 함수 72 개(생성기 6,781 줄 가운데): 정수로 · RMS 정규화 ·
  정수 타일 판 모두(끝손질 셋 · 열먼저 · 로짓) · 정수 줄 판 · 임베딩 · RoPE+KV · SwiGLU · 가장 큰 번호 · 정수 KV 어텐션(프롬프트 · 갈래 · 묶음 ·
  두 층 · 생성 조각 · 접기) · 칸 판 · 묶은 줄 판 · 생성 메가커널.
- 빌드는 명령 둘: `커널생성 qwen2Q8 qwen2Q8.gl` → `자체PTX qwen2Q8.gl -o qwen2Q8.ptx`.

### 미리 밝혀 둘 것

1. **범위는 Qwen2 모듈**(`qwen2Q8.gl` — 실행기가 쓰는 것). GPT-2 의 모듈 22 개는 파이썬 생성기 그대로 둔다 — 그것을 쓰는 것은 파이썬 연구
   엔진(`엔진/글gpt2.py`, 3 ~ 13단계의 기록)뿐이고 그 엔진은 파이썬이다.
2. **옮기는 것은 Qwen2 설정이 지나는 갈래만.** 다른 설정(짧은실수 · 반실수 KV, F16 · Q4_0, 가닥 계약, 자리 넷)의 갈래는 옮기지 않는다 — 글
   생성기는 Qwen2 설정 밖이면 다른 소스를 내지 않고 멈춘다(거부).
3. **정답지는 파이썬 생성기의 출력이다**(바이트 대조). 견주는 도구는 파이썬이어도 된다 — 빌드와 실행에는 들지 않는다.
4. **파이썬 엔진의 빌드 묶음**(`엔진/커널모듈.py` — 소스 · PTX 캐시)은 파이썬 엔진 쪽에 그대로 둔다. 글 쪽 빌드는 위의 명령 둘이다.

## 결과 (2026-10-11)

**세 판정 모두 통과.** 이제 Qwen2 채팅은 빌드에도 파이썬이 들지 않는다. 글(geul) 언어로 옮긴 커널 생성기는 파이썬 생성기와 바이트까지 같은
커널 소스를 내고, 걸리는 시간은 파이썬 생성기의 0.44 배다. 파이썬이 없는 PATH 에서 자체 호스팅 글 컴파일러가 생성기 · PTX 뒷단 · 실행기를 빌드하고,
생성 → PTX → 채팅까지 가서 18a 와 같은 답을 냈다.

    커널/커널생성.gl … ─(자체 호스팅 글 컴파일러)→ 커널생성.exe ─→ qwen2Q8.gl   (6.8 MB · 0.04 초)
    qwen2Q8.gl ─(글 PTX 뒷단 자체PTX.exe)→ qwen2Q8.ptx                         (52 MB · 26 초)
    호스트/실행기.gl ─(자체 호스팅 글 컴파일러)→ 실행기.exe ─(kernel32 · shell32 · nvcuda.dll)→ GPU

가변 인자 함수 `서식글` 의 형식 자리)로, 람다는 틀(`@` 자리를 값으로 바꾸는 글 — `틀채우기`)로, 함수 안의 함수는 바깥의 값을 전역으로 받는 함수로

### 밝혀 둘 것

1. **예비 재기에서 19c 를 넘지 못했고, 공식 실행 전에 고쳤다.** 처음으로 바이트가 같아진 판(00:36)은 다섯 번에 131.6 / 122.2 / 120.1 / 119.9 / 121.4 ms 가
   걸렸다. 파이썬은 바이트코드 캐시가 있으면 85 ~ 90 ms 다. 출력은 그대로 두고 아래 넷을 고쳤고, 고칠 때마다 해시를 견주었다.
   - **서식**: 표준 `서식화` 는 바이트마다 함수를 부른다. 끼워 넣기가 만드는 서식(%s · %lld · %%)만 다루는 `서식글` 로 바꾸고, 형식마다 조각을
     한 번만 풀어 둔다(형식은 리터럴이라 주소가 바뀌지 않는다). 이것으로 약 89 ms.
   - **줄 목록**: 표준 `문자열목록_추가` 는 넣을 때마다 글을 복제한다(할당 + 복사). 주소만 담는 목록으로 바꿨다.
   - **길이 세기**: 8 바이트씩 센다.
   - **줄 잇기**: 길이를 먼저 세어 메모리를 한 번에 잡는다. 여기까지 약 42 ms.

   마지막으로 서식 캐시의 표를 전역 배열에서 힙으로 옮겼다. 0 으로 시작하는 전역 배열도 실행 파일에 그대로 들어가서 생성기가 2,094,080 B 였다
   (옮긴 뒤 325,120 B).
2. **공식 실행은 두 번이다.** 00:42:27 의 첫 실행(전역 배열 판 — 생성기 2,094,080 B, `11361f55…`)도 결과가 같았다. 생성 75 ms · PTX 25.7 초였고 해시가
   같았으며, 답도 같았다(다른 것은 올림 0.4 초 대 0.3 초 한 줄). 생성기를 줄인 뒤 00:43:32 에 다시 돌렸다. 판정은 이 둘째 실행과, 그 생성기로 잰
   19c 로 한다. 첫 실행의 기록은 [결과/19단계/19ab_기록_첫실행.txt](결과/19단계/19ab_기록_첫실행.txt).
3. **생성된 소스의 머리 주석**은 "커널생성.py 가 만든 파일 — 고치지 말 것." 그대로다. 바이트까지 같아야 하기 때문이다(19a).
4. **컴파일러의 씨앗.** 자체 호스팅 글 컴파일러의 1세대는 파이썬 참조 구현이 만든다(`build.py selfhost` — 그 뒤 2 · 3세대가 같은 바이트인 고정점).
   자체 호스팅 언어라면 누구나 겪는 씨앗 문제다. 배포판(글 1.x 의 `geulc.exe` — 자기 컴파일한 실행 파일)을 받으면 파이썬이 들지 않는다. 위의
   배포판 확인이 그 길이다. 연구 가지의 컴파일러와 배포판의 차이는 연구 옵션(반실수 · 조각 모드)뿐이고, 이 옵션은 기본으로 꺼져 있다. GitHub 의
   2g-1.2.1 배포물은 이 PC 의 zip 과 바이트가 달라(`build.py wheel` 이 zip 을 다시 썼다), 그 안의 `geulc.exe` 와는 견주지 않았다.
5. **남은 파이썬** — 어느 것도 Qwen2 채팅의 빌드 · 실행에는 들지 않는다.
   - GPT-2 의 모듈 22 개와 그것을 쓰는 파이썬 연구 엔진(`엔진/글gpt2.py` · `엔진/커널모듈.py` · `커널생성.py` 의 GPT-2 갈래) — 미리 밝혀 둔 1 · 4
   - 대조용: 파이썬 호스트(`엔진/글qwen2.py` · `실행.py`), 파이썬판 PTX 컴파일러(`컴파일러/글ptx.py`)
   - 정답지 · 시험 · 재기(`계약/정수계약.py` · `시험/` · `재기/`)
   - GPT-2 모델 파일 준비(`준비/gguf쓰기.py`)
6. **글(geul) 언어에 대해 알게 된 것** (언어 쪽 기록)
   - **이름이 정확히 같은 함수가 동사 풀이보다 먼저다(D-37).** 생성기의 `다듬기` 가 표준/서식.gl 안의 `다듬다` 부름을 가로채서
     "'큰수 참조'를 '문자열'에 넣을 수 없습니다" 가 났다. `정수로` 도 같은 꼴이었다. 표준 라이브러리 안의 부름이 쓰는 쪽의 함수 이름에 따라 바뀐다.
   - **리터럴은 다른 쪽 피연산자의 형을 따른다(명세 3.8).** 그래서 `(문자 & 63) << 6` 이 8 비트로 계산되어 소리 없이 잘린다(1088 → 64).

   - 같은 형의 매개변수 둘에 조사가 다르면, 부르는 쪽에도 조사를 붙여야 한다(D-30).
   - 끼워 넣기의 중괄호 안에는 문자열 리터럴을 쓸 수 없다. 미리 변수에 담는다.
   - 큰 일에서는 표준 `문자열목록_추가`(복제) · `서식화`(바이트마다 부름) · `메모리_비교`(바이트마다)가 느리다.
   - 0 으로 시작하는 전역 배열도 실행 파일에 들어간다.
