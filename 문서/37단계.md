# 37단계 — Qwen3: 두 번째 모델 계열 (사전 등록 2026-10-15)

모델 다양성의 2단계다(1단계는 앱의 'Hugging Face에서 찾기' — 36g). 지금 엔진이 받는 구조는 qwen2 하나(Qwen2.5 · DeepSeek-R1-Distill-Qwen)다.
Qwen3 는 같은 토크나이저(BPE 어휘 151,936 · pre qwen2)를 쓰고 블록의 차이가 작아 다음 계열로 가장 가깝다: **머리마다 Q · K 정규화**(RMSNorm,
RoPE 앞), **Q · K · V 치우침 없음**. 공식 GGUF 의 형식(Q8_0 순수 · Q4_K_M = Q4_K + Q6_K)은 엔진이 이미 받는다.

판정 기준을 결과보다 먼저 적는다.

## 검증의 단위 — 모델마다가 아니라 구조 · 모양 · 형식마다

사용자(2026-10-15): 모델을 하나씩 더하면 모든 모델을 이 PC 에서 돌려야 하는데 그건 불가능하고, 130B 같은 큰 모델은 시험조차 못 하지 않나.

비트까지 같다는 것은 판(커널)과 그 짜임의 성질이고, 판은 **구조**(블록의 정의) · **모양**(너비 · 머리 · KV 머리 · FFN · 어휘) · **형식**(Q8_0 ·
Q4_0 · k-양자화)에만 달려 있다 — 가중치의 값에는 달려 있지 않다. 그래서 검증의 단위는 셋이다.

1. **구조**: 실제 모델 하나(작은 것 — 이번에는 Qwen3-1.7B)로 끝에서 끝, 그리고 계약 · CPU 참조.
2. **모양**: 엔진은 모양 규칙(머리 128 · 질의 폭 = 너비 · 너비는 256 의 배수 · FFN 은 64 의 배수(k-양자화는 256) · 머리 / KV 머리 ≤ 16)을 지키는
   모양마다 판을 만든다. 큰 모양은 **합성 모델**(실제 크기의 행렬 · 층 몇 개 · 무작위 값 — 24단계의 32B · 72B 와 같은 길)로 비트를 본다 —
   층은 모두 같은 판으로 돌므로 층 수는 판의 길을 바꾸지 않는다.
3. **형식**: 형식마다 판 시험(무작위 활성값 + 실제 가중치).

미세조정 모델(Hugging Face 의 수백 개)은 바탕 모델과 구조 · 모양이 같아 따로 볼 것이 없다 — 앱의 받기 전 확인이 파일 머리로 구조 · 모양 ·
형식이 검증된 범위인지 본다(36g). 실제 큰 모델은 **비트는 합성 모델로 확인하지만, 돌리기와 속도는 이 PC(12 GB)로 할 수 없다** — 72B 의 Q4 는
40 GB 남짓이라 GPU 여러 장(25단계의 층 나누기 — 이 PC 에서는 흉내)이 필요하다. 130B 이상의 속도 주장은 하지 않는다.

## 무엇을 만드나

1. **계약(문서/계약.md 4절에 4.6).** 머리마다 Q · K 정규화: 4.1 의 RMSNorm 을 행 · 머리마다 D = 128 로(가닥 t < 128 에 한 칸씩 — 128 접기는 +0,
   그다음 64 · 32 · … · 1 로 반씩 접음), 무게는 `attn_q_norm` · `attn_k_norm`(F32 128 칸), eps 는 파일의 값. 차례: q · k · v 선형(치우침 없는 선형은
   4.5 대로 0 을 더함) → q · k 의 머리마다 정규화 → RoPE(4.2 · 머리 128 의 짝 (i, i + 64)) → 자리 둘 · 정수 KV. v 는 정규화하지 않는다.
2. **CPU 참조(파이썬 — 대조 도구).** `시험/참조7B.py` 를 qwen3 로 넓힌다(`qwen3.*` 열쇠, 치우침 없음, q · k 정규화, 묶인 출력),
   `계약/정수계약.py` 에 머리 정규화.
3. **글 생성기.** 모듈 `qwen3{Q8|K}_{너비}x{머리}x{KV}x{FFN}x{낱말}` = 지금의 머리 128 모듈 + **머리 정규화 판 하나**(버qkv 위에서 제자리 —
   매개 4 개 이하, 위치와 상관없어 프롬프트 · 생성 그래프 · 서버 표 셋이 함께 쓴다). RoPEKV 판들은 바이트까지 그대로 둔다(정규화를 RoPEKV 에
   합치면 매개가 14 ~ 15 개로 AMD 의 밀기 상수 한도 13 개를 넘는다 — 합치기는 속도 지렛대로 남긴다). qwen2 모듈의 소스 · PTX · SPIR-V 는
   바이트까지 그대로.
4. **글 호스트.** 설정읽기가 qwen3 를 받는다(key_length · value_length = 128, 질의 폭 = 128 × 머리수 = 너비 — 이번 범위, eps 가 생성기 상수와
   다르거나 RoPE 늘이기가 있으면 거절). 치우침 텐서가 없으면 영치우침을 쓰고, 층마다 q · k 정규화 무게를 올리고, 정규화 판을 RoPEKV 앞에
   띄운다(큰층띄움들 · 생성계획짓기 · 표계획짓기). 모듈 이름 · 앱의 모듈 준비.
5. **서버 · 토크나이저 · 앱.** Qwen3 채팅 틀(기본 시스템 말 없음, 생각 끔은 `<think>\n\n</think>\n\n` 를 앞에 붙임), **종류 4 토큰을 글로 내는
   켜기**(요청의 `geulpu.special` — 기본은 지금처럼 꺼짐이라 교차검증의 글은 그대로. 서버 해시는 이 단계에서 어차피 바뀐다). 앱: 목록에
   Qwen3-8B Q8_0 · Q4_K_M · 1.7B Q8_0(· 14B Q4_K_M), 받기 전 확인 · 검색의 구조 qwen3, 생각 접기를 토큰 번호(151668)로, 생각 켬 · 끔.

범위 밖(다음 단계): 질의 폭 ≠ 너비(Qwen3-0.6B · 4B · 32B), MoE(Qwen3-30B-A3B · 235B-A22B), 공유32 장치의 k-양자화(AMD 8 GB — 아래).

### 미리 밝혀 둘 것

1. 파일은 Qwen 공식 GGUF 를 받는다(머리는 위에서 확인). 정확도는 판정이 아니다 — 엔진이 CPU 참조(계약)와 비트까지 같은지가 판정이다.
2. 머리 정규화는 판 하나를 더 띄운다(층마다 한 번). llama.cpp 도 q · k 정규화를 따로 셈하지만 판을 합치는지는 백엔드마다 다르다 — 같은 최적화
   수준의 값을 보려고 정규화 판의 시간을 기록으로 따로 적는다.
3. 공유32 장치에서 Qwen3-8B Q8_0(8.11 GB)은 그래픽 메모리 16 GB 이상에서만 들고, Q4_K_M 은 공유32 가 k-양자화를 받지 않아 안 된다. 그래서
   공유32 는 1.7B Q8_0 으로 비트만 본다(AMD 한도 흉내).
4. 대조 도구(CPU 참조 · 견주기)는 파이썬이다. 엔진 · 생성기 · 실행기 · 서버는 글이다(모든 GPU 코드는 글 컴파일러의 PTX · SPIR-V 뒷단).
5. 사용자가 계획과 받기를 확인했다(2026-10-15 — "진행해"). 이 문서를 커밋한 뒤에 구현 · 측정한다. 합성 모델(37a(5))은 사용자의 물음에 답해
   계획에 더했다 — 14B 는 받지 않고 모양만 본다.

## 설계 — 머리 정규화 판

- 이름 `머리정규화128`(모듈 끝에 붙인다 — 앞의 판은 한 글자도 바뀌지 않는다, 28 · 32단계와 같은 꼴). 매개 넷: 버qkv(짧은실수 [행][QKV폭]),
  q 무게 · k 무게(층의 128 칸 — 호스트가 층마다 주소를 준다), 행 수. 위치와 상관없어 칸판(걸음칸) 변형이 필요 없다 — 생성 그래프는 행 수를
  붙잡아 둔 그대로, 서버 표는 그 걸음의 행 수로.
- 워프 하나 = (행, 머리) 하나(q 머리 NH 개 + k 머리 NKV 개). 레인 l 이 d = l + 32·i (i = 0 … 3)를 맡으면 계약의 접기가 그대로 나온다:
  p_d = x_d · x_d → 64 접기 a = p_l + p_{l+64}, b = p_{l+32} + p_{l+96} → 32 접기 a + b → 셔플 xor 16 · 8 · 4 · 2 · 1(덧셈은 교환 법칙이 있어
  두 레인이 같은 비트) → S. r = 1 / 제곱근(S / 128 + eps)(나눗셈 · 제곱근은 바르게 반올림 — PTX `.rn` · SPIR-V 뒷단 31e), y_d = (x_d · r) · w_d.
- 공유 메모리를 쓰지 않고 밀기 상수 매개 넷이라 공유32 · 밀기 128 바이트 장치(AMD)에서도 그대로 돈다.

## 미리 짚어 둘 위험

- **어휘 151,936 은 256 의 배수가 아니다**(128 의 배수). 머리 128 모듈은 152,064(256 의 배수)로만 만들어 왔다 — 로짓 타일 판의 꼬리 나누기 ·
  가장큰번호 · k-양자화 임베딩에서 가정이 있는지 37a(2) 전에 판 시험으로 먼저 본다.
- **묶인 출력(1.7B)**: 머리 128 의 묶인 출력은 처음이다(0.5B 는 머리 64). 엔진의 길(출력 = 낱말표)은 있다.
- **서버 해시가 바뀐다**: 꾸리기 · runV 가 기준 해시와 견주므로 expected.json 을 고친 커밋 전에는 릴리스 CI 가 멈춘다(설계대로 — 37b(3) 뒤에 고친다).
- **생각 켬이 기본**: Qwen3 는 기본으로 생각을 쓴다. 채팅 틀이 끔을 고르면 `<think>\n\n</think>\n\n` 를 붙인다 — 공식 틀과 같은 글이어야
  한다(GGUF 의 chat_template 과 견줌).

## 구현 (2026-10-15)

- **계약 · CPU 참조**: [계약.md](계약.md) 4절 6(머리마다 Q · K 정규화 — 4.1 의 RMSNorm 을 D = 128 로), `계약/정수계약.py` 의 `머리정규화`
  (행 · 머리를 [행 × 머리][128] 로 펴서 `rms정규화`). 계약 자체 시험(빠른 점검)에 둘을 더했다: 판의 차례(레인 l 이 d = l + 32·i, 64 접기를
  둘로 · 셔플 xor)가 계약의 접기와 비트까지 같고 모든 레인이 같은 S 를 갖는지(4,096 머리 — 0 · 비정규수 · 2 의 거듭제곱 섞음), fp64 의 정규화와의
  상대 오차(최대 2.2 × 10⁻⁷). `시험/참조7B.py` 는 앞으로를 함수로 떼고 qwen3 를 받는다(열쇠 앞머리 · 치우침 없으면 0 · q · k 정규화 ·
  묶인 출력 · key_length).
- **생성기**: `커널생성 qwen3큰 <형식> <너비> <머리> <KV> <확장폭> <낱말> <출력.gl>` = `qwen2큰` 의 모듈 + 모듈 끝에 `머리정규화128` 하나.
  PTX 는 계약의 차례 그대로다(`mul.rn.ftz` · `add.rn.ftz` · `shfl.sync.idx` 다섯 · `div.rn.ftz` · `sqrt.rn.ftz`). 빠른 점검의 모듈 줄에 qwen3
  넷(1.7B Q8_0 · 8B Q8_0 · 8B K · 1.7B Q8_0 공유32)을 더했고 옛 줄 아홉은 바이트까지 그대로다.
- **호스트**: 설정읽기가 qwen3 를 받는다(key_length · value_length 128, 질의 폭 = 너비, eps 10⁻⁶, RoPE 늘이기 없음 — 아니면 까닭을 적고
  멈춤). 치우침 텐서가 없으면 그 칸은 0(버퍼를 0 으로 잡는다), 층마다 q · k 정규화 무게 256 칸. 정규화 판은 qkv 선형 뒤 · RoPEKV 앞의 세 곳
  (프롬프트 길 · 생성 그래프 · 서버의 표 걸음)에서 띄운다. 층 나누기(25단계)의 조각 상태, 진단 · 재기 도구의 판 나누기에도 넣었다(재기_7B커널은
  `q·k정규화` 를 따로 적는다).
- **서버 · 실행기**: Qwen3 의 채팅 틀(GGUF 의 chat_template 과 같은 글 — 기본 시스템 말 없음, 마지막 질문 앞의 답은 생각을 떼고, 생각 끔은
  요청의 `chat_template_kwargs.enable_thinking` — llama-server 와 같은 열쇠), `geulpu.special` 이 참이면 사용자 정의 토큰(종류 4 — `<think>` ·
  `</think>`)을 글로 낸다(기본은 꺼짐 — R1 교차검증의 글은 그대로). 실행기는 Qwen3 에 기본 시스템 말을 넣지 않는다.

## 결과 (2026-10-15)

공식 실행(`공식37.sh`)은 돌리지 않았다. 사용자의 결정이다(2026-10-15): 이번 일은 계약 · 공유 판을 바꾸지 않고 받는 범위를 넓힌 일이라,
커밋할 코드와 같은 코드로 이미 돌린 비트 시험을 다시 돌려도 새로 증명되는 것이 없다. 아래 비트 결과는 **커밋 전 같은 코드**로 돌린 것이고,
커밋에서는 빠른 점검(CI)이 모듈 열셋(옛 아홉 + qwen3 넷)의 바이트를 다시 본다.

- **37a 통과.**
  1. 머리 정규화 판: Qwen3-8B 의 실제 무게(36 층의 q · k 정규화) + 무작위 q · k, 행 1 · 4 · 64 · 2048 — q · k 다른 칸 0, v 는 그대로
     (CUDA · Vulkan 모두).
