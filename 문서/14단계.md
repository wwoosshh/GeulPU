# 14단계 — 첫 채팅 모델: Qwen2.5-0.5B-Instruct (Llama 계열 블록) (2026-10-10)

사용자 결정: GeulPU 로 옮긴 뒤 "다음 단계 진행해" — Llama 계열의 첫 채팅 모델과 터미널 실행기. 모델 받기 허락(같은 날): Qwen2.5-0.5B-Instruct
의 공식 Q8_0 GGUF 와 원본(safetensors · 토크나이저). 이 문서는 연구 계획이다 — 판정 기준을 결과보다 먼저 적고(이 커밋), 결과가 나오면
상태 칸만 고친다(연구 0~13단계의 규칙 그대로 — [단계기록](단계기록.md)).

## 모델

- **Qwen2.5-0.5B-Instruct** (Apache 2.0). 엔진이 읽는 파일: 공식 GGUF `Qwen/Qwen2.5-0.5B-Instruct-GGUF` 의 `qwen2.5-0.5b-instruct-q8_0.gguf`
  (675,710,816 바이트, SHA-256 ca59ca7f…76844e — 확인함). 텐서는 Q8_0 170 · F32 121 뿐 — `output.weight` 가 `token_embd.weight` 와
  따로 있고 값이 같다. 원본 `Qwen/Qwen2.5-0.5B-Instruct`(safetensors bf16 988,097,824 바이트, SHA-256 fdf756fa…288fb7fe — 확인함)는
  토크나이저 · 참값 계산의 대조에 쓴다.
- **구조**: 층 24, 너비 896, 질의 머리 14 · KV 머리 2(GQA 7:1), 머리 64, MLP 4864(SwiGLU), RMSNorm(eps 10⁻⁶), RoPE(NeoX — 반쪽 돌리기,
  θ = 10⁶), q · k · v 의 치우침(o · MLP 는 없음), 어휘 151936, 위치 32768. GPT-2 와 다른 것: RMSNorm · RoPE · SwiGLU · GQA · 위치 임베딩
  없음 · 치우침 없는 선형.
- **판정 전에 찾은 것 — GGUF 의 판.** 공식 GGUF 는 지금의 원본 safetensors 와 **다른 판(체크포인트)** 에서 만든 것이다: 층의 선형
  가중치 · 층 정규화 가중치가 20~50% 다르다(같은 층끼리 가장 가깝다). 치우침 · 낱말표 · 마지막 정규화는 같다. 두 판 모두 제대로
  답한다("Paris", "대한민국의 수도는 서울입니다."). 그래서 원래 모델 대비 "형식의 손실" 은 이 파일로 잴 수 없고, **정확도의 기준은
  GGUF 의 가중치를 그대로 푼 fp64 참값**이다 — 엔진이 같은 가중치로 계산에서 더 잃는 몫(숨은 손실)만 잰다(연구 5단계의 잣대).
  참값 계산(시험/참값.py — fp64 끝까지)은 원본 가중치로 HF transformers(fp64 — RMSNorm 만 fp32)와 행 상대차 최대 2.6 × 10⁻⁶.

## 계약 — 새 블록 (정수 블록 계약 · 정수 KV 계약에 더한다 — [계약](계약.md))

1. **임베딩**: token_embd 의 행을 푼다(q · d — 정확, 짧은실수). 위치 임베딩은 없다.
2. **RMSNorm** (행 하나, 너비 D): 가닥 t (0 … 255)의 부분합 p_t = Σ_{c ≡ t (mod 256), c 오름차순} (x_c · x_c) — 곱 · 합마다 반올림;
   p 를 128 부터 반씩 접어(p_t ← p_t + p_{t+접기}) 합 S; 평균제곱 = S / D; r = 1 / 제곱근(평균제곱 + eps) (나눗셈 · 제곱근은 IEEE 의
   가까운 반올림, eps = 짧은실수(10⁻⁶)); y_c = (x_c · r) · w_c (반올림 둘). 다음 선형 층의 입력이면 바로 자리 둘로. (GPT-2 층정규화의
   차례와 같은 꼴.)
3. **RoPE**: 표 cos · sin [위치][32] 는 호스트가 fp64 로 계산해 짧은실수로 반올림(θ_i = θ^(−2i/64), 각 = 위치 · θ_i — fp64). q 의 머리마다
   i < 32: q′_i = 곱해더하기(q_i, cos, −(q_{i+32} · sin)), q′_{i+32} = 곱해더하기(q_{i+32}, cos, q_i · sin) — 짧은실수, k 도 같게. 그다음
   q 는 자리 둘, k · v 는 정수 KV 캐시로(정수 KV 계약 그대로).
4. **GQA**: 질의 머리 h 는 KV 머리 ⌊h / 7⌋ 의 캐시를 읽는다 — 어텐션의 계약(점수 · 적힌지수 · 정수 합 · 두 층 접기)은 그대로.
5. **SwiGLU**: g · u 는 정수 블록 계약의 선형 둘(gate · up). e = 적힌지수(−|g|), s = g ≥ 0 이면 g / (1 + e), 아니면 (g · e) / (1 + e)
   (지수의 인자가 늘 0 이하 — 넘치지 않는다), h = s · u — 연산마다 IEEE 반올림. h 는 down 의 입력이라 바로 자리 둘로.
6. **치우침 없는 선형**(o · gate · up · down · 로짓)은 치우침 0 을 더한다(GPT-2 와 같은 끝손질 — 값이 같다).
7. **로짓**: output.weight(Q8_0)의 정수 블록 계약 선형 → 탐욕(가장 큰 값의 번호, 같으면 작은 번호).

계약이 정한 값이니 프롬프트 · 하나씩 · 나눠 넣기 · 대화 어느 길로 계산해도 같은 비트이고, CPU 참조(계약/정수계약.py 에 Qwen2 를
더한다)가 같은 비트를 낸다.

## 결과 (2026-10-10)

### 만든 것

- **계약 · CPU 참조** ([계약/정수계약.py](../계약/정수계약.py)): `rms정규화` · `rope표` · `rope` · `swiglu` 와 Qwen2 의 전체 앞으로
  `qwen2_앞으로`(정수 블록 계약 · 정수 KV 계약 · 두 층 접기 그대로, GQA 는 KV 머리 ⌊h/7⌋).
- **커널** ([커널생성.py](../커널/커널생성.py) `qwen2_source` → `qwen2Q8.gl`, 69,600 줄 남짓):
  - RMS정규화정수줄 — RMSNorm 을 하고 그 자리에서 자리 둘로 바꾼다.
  - 타일 끝손질 `_QKV정수` — 워프의 열 64 개가 머리 하나라, 열 i 와 i+32 가 같은 스레드에 있다. 레지스터 안에서 치우침 · RoPE 를 하고
    q 자리 · KV 캐시를 쓴다.
  - 타일 끝손질 `_SwiGLU정수` — gate · up 을 32 열씩 번갈아 깔아, silu(g)·u 를 down 의 자리 둘로 바로 쓴다.
  - 줄 길의 묶은 판(정수줄선형QKV · gu · 로짓) — RMSNorm · RoPE+KV 바꾸기 · SwiGLU · 블록마다의 가장 큰 값을 행렬곱 커널에 묶는다.
  - 열먼저 타일 판 — 같은 칸 계산에 블록 차례만 바꾼다.
  - 생성 그래프의 칸 판 — 위치 · 걸음을 GPU 의 걸음칸에서 읽는다.
  - 어텐션 커널은 9~13단계의 것 그대로에, KV 머리의 자리만 `KV머리식`(GQA)으로 바꿨다.
- **엔진** ([엔진/글qwen2.py](../엔진/글qwen2.py)): GGUF(Q8_0)를 정수 배치로 깐다(값 그대로).
  - 프롬프트(행 다섯 이상)는 타일 판 · 13단계 어텐션 판 · CUDA 그래프로 돈다.
  - 줄 길(행 넷까지)은 묶은 판으로 돈다.
  - 생성은 **고치지 않는 그래프 하나를 걸음마다 다시 띄운다** — 가장큰번호칸이 다음 토큰을 쓰고 걸음칸을 올리므로, 호스트는 걸음마다
    기다리지 않는다.
  - 판 고르기 · 꼬리 자르기 · 계획 · 그래프 장치는 글GPT2 의 것을 물려받는다.
- **토크나이저**는 GGUF 안의 것(`tokenizer.ggml.*`)으로 만든다. 낱말 151,643 · 병합 151,387 · 특수 22 개가 HF 파일과 같음을 확인했다.
- **터미널 실행기** [실행.py](../실행.py): GGUF 하나를 받아 ChatML 로 채팅한다.
  - 답을 흘려 보이고, 차례마다 KV 캐시를 이어 쓰고, 탐욕으로 고른다.
  - 차례 덩이의 머리는 앞 답의 마지막 토큰이다 — 그래서 대화 전체를 한 번에 넣은 탐욕과 토큰까지 같다.

바닥과의 거리(생성): 가중치 525 MB 를 한 번 읽는 바닥 1.04 ms 의 1.56 배(채팅 질문). 문맥 8192 는 KV 를 더해(위치마다 층 24 × KV 머리 2 ×
260 바이트) 바닥 1.24 ms 의 1.61 배. 커널 147 개(층마다 6)의 띄움 사이와 작은 행렬곱(QKV 18 블록 · o 32 블록)의 지연이 남은 몫이다 —
생성 메가커널(다음 단계)의 몫.

### 밝혀 둘 것

1. **평가글의 토큰 수.** 이 문서는 "평가글 512 토큰" 이라고 적었다. 그러나 평가글은 Qwen 토크나이저로 **461 토큰**이라, `[:512]` 가 전체를
   담았다. llama.cpp 의 기준값(기준14 — 판정 전에 잰 것)도 같은 461 토큰 위에서 쟀으므로 견주기는 같은 열이다. 고친 것은 글자뿐이다.
2. **RoPE 표.** 표는 "fp64 로 계산해 짧은실수로 반올림" 한다고 적었다. 플랫폼의 수학 함수와 상관없게 이를 좁혔다.
   - θ_i 는 십진 60 자리(파이썬 표준 decimal)로 구해 fp64 로 바르게 반올림한다.
   - 각 = 위치 · θ_i 는 fp64 곱(IEEE)이다.
   - cos · sin 은 짧은실수로 바르게 반올림한다 — 한가운데에 가까운 값만 십진 80 자리로 다시 구한다.
   엔진과 CPU 참조가 같은 함수(`정수계약.rope표`)를 쓴다.
3. **찾은 것 — 적힌지수의 가림.** 커널생성.py 의 `적힌지수식` 은 목적이 선언("짧은실수 e")일 때 끝 줄 `x < −87.3 이면 { 짧은실수 e = 0 }`
   이 안쪽 블록에 새 변수를 만든다(글은 안쪽 블록의 가림을 받는다). 그래서 바깥 e 가 0 이 되지 않고, 비정규수 크기(≤ 2⁻¹²⁶)의 다항식
   값이 남는다.
   - 이 꼴은 9~13단계의 정수 KV 어텐션 모든 판(프롬프트 · 생성 · 접기 · 메가커널)에 있다.
   - 가려진 키에서도 그 값이 남는다. 그래도 GPT-2 의 결과에는 드러나지 않았다 — 9~13단계의 CPU 대조가 모두 같았다:
     - 합 l 에서는 2⁻²³ 눈금의 가까운정수가 0 이다.
     - 가중합 · 접기에서는 남는 몫이 2⁻¹²⁶ · |v| 남짓이다. 조각의 최댓값을 가진 키의 몫(정규수 크기)에 더할 때 반올림에서 사라진다.
     - 비트가 갈리는 것은 그 몫이 정확히 0 인 드문 경우(예: 값이 모두 0)뿐이다.
   - GPT-2 모듈의 소스를 그대로 두려고(14a(4)) 고침은 깃발 `적힌지수가림고침` 으로만 했다. qwen2 모듈만 켠다: 선언과 대입을 나눠 0 이
     바깥 변수에 들어가게 한다.
4. **열먼저 판.** 첫 속도 확인에서 프롬프트 8192 의 down 행렬곱이 층마다 2.6 ms 였다(2048 의 4배인 0.8 ms 보다 길다). 입력 자리(80 MB)가
   L2(48 MB)를 넘는데 블록이 행 먼저 돌아, 열 블록마다 입력을 DRAM 에서 다시 읽었기 때문이다.
   - 블록 번호의 가로 · 세로만 바꾼 열먼저 판을 더했다. 칸마다의 계산은 같다 — 판 12 개(행먼저 6 · 열먼저 6)를 하나씩 강제한 전체
     앞으로가 CPU 참조와 모두 비트까지 같았다.
   - 판 고르기가 재서 고른다. 프롬프트 8192 가 196.8 → 159.3 ms(비공식)가 되었다.
5. **로짓 가중치.** GGUF 의 `output.weight` 가 `token_embd.weight` 와 바이트까지 같아서(엔진이 올릴 때 확인) GPU 에 한 벌만 둔다. 값은 같다.
6. **생성 길.** 계획대로 생성 메가커널은 다음 단계로 미뤘다. 그 대신 따로 도는 커널의 그래프에 줄 길의 묶은 판을 넣었다.
   - 처음 판(RMS · RoPE · SwiGLU · 가장큰번호가 따로)은 토큰당 2.07 · 2.14 · 2.45 ms(비공식)로 llama.cpp 보다 느렸다.
   - 묶은 판으로 커널이 244 → 147 개가 되었다. 두 판 모두 비트가 같다 — 시험에서 대조함.
7. **시험의 이력.** 14a 의 전체 시험은 세 번 돌았다.
   - 첫 번째(14e 시험을 넣기 전)는 모두 통과했다.
   - 두 번째(14e 를 더한 것)는 14e 가 실패였다. 실행기의 표준 출력이 윈도에서 `\r\n` 이라, 여러 줄인 셋째 답이 대화 시험의 답(`\n`)과
     글자가 달랐다. 시험이 `\r\n` 을 `\n` 으로 읽게 고쳤다 — 실행기와 엔진은 그대로다.
   - 그 실행은 끝나기 전에 멈추고, 세 번째로 공식 기록(빌드/결과/시험14.json)을 냈다.
8. **속도를 잰 뒤에 고친 것**(잰 길과 상관없다).
   - 실행기의 생성이 걸음을 1 · 2 · 4 · 8 · 16 개씩 띄운다. 짧은 답에서 끝 토큰 뒤의 헛걸음을 줄인다 — 2 토큰 답이 35 → 521 토큰/초로
     보인다.
   - 생성 그래프를 판 고르기 때 미리 만든다.
   - 잰 길(`글Qwen2.생성` — 프롬프트 계획 + 생성 그래프를 n − 1 번 잇따라)은 바뀌지 않았고, 값은 같다(14a).
9. **실행기가 numpy 만으로.** 판정 뒤, 릴리스 전에 고쳤다. 처음 판의 RoPE 표는 바른 반올림에 mpmath 를 썼는데, 보통 파이썬에는 없어
   README 대로(`pip install numpy`) 실행기가 시작하지 못했다(시험 · 재기는 mpmath 가 있는 환경에서 돌았다). 표준 라이브러리 decimal 로
   바꿨다 — 위치 32768 까지 cos · sin 표가 mpmath 판과 비트까지 같고(한가운데에 가까워 다시 구하는 칸은 이 범위에 없다), 다시 구하는 식
   (decimal 의 cos · sin)도 무작위 각 300 개에서 mpmath 와 10⁻⁵⁵ 안에서 같다. 값은 바뀌지 않는다.
