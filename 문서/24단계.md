# 24단계 — 설정에서 모델 모양 만들기: 14B · 32B · 72B (2026-10-11)

사용자 방향(2026-10-11, 23단계에 적은 것): 로컬 AI 를 실제로 쓰는 사람들은 12B · 30B · 120B 를 돌린다. 추천 순서의 (2)가 이 단계다 —
커널 생성기와 호스트가 모델의 모양을 GGUF 의 설정에서 받게 한다. **시험은 이 PC(RTX 4070 Ti 12 GB 한 장) 안에서만** 한다.
사용자 허락(2026-10-11): Hugging Face `Qwen/Qwen2.5-14B-Instruct-GGUF` 의 공식 q4_0 세 조각(8,517,725,856 B)을 받는다.

판정 기준을 결과보다 먼저 적는다.

## 왜

커널은 모델의 모양(너비 D · 머리 수 · KV 머리 수 · 확장폭 F · 낱말 수 V)을 상수로 담아 만든다. 22 · 23단계의 생성기는 7B 의 모양을
`큰모델설정` 에 적어 두었고, 호스트의 `설정읽기` 는 0.5B 와 7B 의 모양 둘만 받았다. 그래서 14B 이상은 돌릴 수 없었다. 생성기 · 호스트의
나머지(판의 식, 계약, 그래프)는 모양과 상관없게 짜여 있다 — 모양을 받는 자리만 열면 된다. 다만 12 GB 에 들지 않는 32B · 72B 는 이 PC 에서
실제 모델로 돌릴 수 없으므로, 실제 모양에 층만 줄인 합성 모델로 시험한다.

## 무엇을 만드나

1. **생성기(글)**: `커널생성 qwen2큰 <형식 Q8_0|Q4_0> <D> <머리 수> <KV 머리 수> <F> <V> <출력.gl>` — 머리 크기 128 의 Qwen2 모듈을 그 모양으로
   낸다. 7B 의 이름(`qwen2Q8_7b` · `qwen2Q4_7b`)은 이 길에 7B 모양을 넣은 것과 같다. 0.5B(`qwen2Q8`, 머리 64)는 그대로 둔다.
2. **호스트(글)**: `설정읽기` 가 머리 크기 128 의 Qwen2 를 모양과 상관없이 받는다(조건: D 가 256 의 배수, 머리 수가 KV 머리 수의 배수이고
   그 비가 16 이하, F 가 64 의 배수). 실행기 · 시험 · 재기 도구는 모양에서 모듈 이름(`qwen2{형식}_{D}x{머리}x{KV}x{F}x{V}.ptx`)을 만들어 찾고
   (7B 는 옛 이름도), 없으면 만드는 명령을 알린다. 문맥(최대길이)은 장치에 들도록 고른다(가중치 · KV 캐시 · 일 버퍼를 세어 8448 이 들지
   않으면 줄인다 — 고른 값을 알린다).
3. **14B 파일은 이 PC 에서 만든다**: 받은 공식 q4_0 (출력 가중치는 Q6_K)을 `llama-quantize --allow-requantize --pure` 로 모든 텐서가 Q4_0 인
   파일로(23단계의 7B 와 같은 길 — 글과 llama.cpp 가 같은 파일을 쓴다).
4. **합성 모델(파이썬, `준비/`)**: 32B(D 5120 · 머리 40 · KV 8 · F 27648)와 72B(D 8192 · 머리 64 · KV 8 · F 29568) 모양, V 152064, 층 넷,
   무작위 가중치(정한 씨앗 — Q4_0 · Q8_0 블록을 바로), 토크나이저 메타데이터는 7B GGUF 의 것. llama.cpp 도 읽는 GGUF 다.
5. **시험 · 대조(파이썬)**: 판 시험 · 머리 128 시험 · CPU 참조의 끝에서 끝을 GGUF 의 모양을 읽어 돌게 넓힌다.

장치 메모리(가중치 · KV · 일 버퍼)와 고른 문맥, 바닥(토큰당 읽는 바이트 / 504 GB/s) 대비 배수, 커널마다의 시간, 실행기로 14B 채팅(18a 꼴).

### 미리 밝혀 둘 것

1. **32B · 72B 는 이 PC 에서 실제 모델로 돌리지 않는다**(가중치가 12 GB 를 넘는다). 실제 모양에 층 넷인 합성 모델로 모양의 일반화(비트 · 길)를
   보이고, 속도는 기록으로만 둔다. 72B 의 실제 생성 속도 · 여러 GPU 는 (3)(25단계)의 일이다.
2. **14B 파일은 공식 q4_0 을 다시 양자화해 만든다**(출력 가중치 Q6_K → Q4_0). 두 엔진이 같은 파일을 쓰므로 견주기는 공정하다. 정확도는 이 단계의
   판정이 아니다.
3. **모듈은 모양마다 미리 만든다**(실행기가 스스로 만들지 않는다 — 생성기와 글 PTX 뒷단으로 만드는 명령을 README 에).
4. **14B 의 문맥은 12 GB 가 정한다.** 8448 이 들지 않으면 들어가는 데까지 줄이고, 24d 의 8192 칸이 들지 않으면 그 칸은 "들지 않음"으로 적는다
   (통과로 세지 않는다).
5. **대조 도구는 파이썬이다**(CPU 참조 · 합성 모델 만들기 · 견주기). 엔진 · 생성기 · 실행기는 글이다.

## 결과 (2026-10-11)

**24a · 24b · 24c · 24d 모두 통과.** 14B 생성은 llama.cpp 의 0.982 · 0.986 · 0.994 배 시간(셋 모두 "같다"), 프롬프트는 1.22 · 1.34 배(기록)다.
- 커널 생성기와 호스트가 모델의 모양을 GGUF 의 설정에서 받는다. 머리 크기 128 인 Qwen2 면 모양과 상관없이 모듈을 만들고 돌린다. 0.5B · 7B 모듈은
  바이트까지 그대로다.
- 14B(Qwen2.5-14B-Instruct, 실제 — 층 48)가 글(geul) 언어의 생성기 · 호스트 · 실행기로 돈다. 채팅 질문 셋(프롬프트 + 생성 16 토큰)의 모든 행
  로짓 26,155,008 칸이 CPU 참조와 다른 칸 0 이다. 12 GB 에 문맥 8448 로 든다(재는 동안 장치 메모리 가장 많이 10,250 MiB).
- 이 PC 에 들지 않는 32B · 72B 는 실제 모양에 층 넷인 합성 모델(Q4_0 · Q8_0)로 봤다. 판 · 머리 128 판 · 다섯 길 · 끝에서 끝이 모두 CPU 참조와
  비트까지 같다. 생성은 llama.cpp 의 0.95 ~ 0.98 배 시간이다(기록).
- 14B 를 맞추다 Q4_0 가중치를 Q8_0 크기로 잡던 버그를 찾아 고쳤다. 값은 그대로이고, 7B Q4_0 도 1.9 GB 를 덜 쓴다.

### 만든 것

- **생성기(글)**: `커널생성 qwen2큰 <Q8_0|Q4_0> <너비> <머리> <KV 머리> <확장폭> <낱말> <출력.gl>`. 7B 의 옛 이름은 이 길의 7B 모양과 같다. 받지 않는
  모양(머리 크기 128 · 너비 256 의 배수 · 머리 / KV ≤ 16 · 확장폭 64 의 배수 밖)은 알리고 멈춘다. 모양의 숫자는 `큰모델설정` 한 곳에만 있었다 —
  커널의 식은 그대로다.
- **호스트(글)**: `설정읽기` 가 머리 크기 128 의 Qwen2 를 모양과 상관없이 받는다. `모듈이름()` 이 모양에서 PTX 이름을 만들고(7B 는 옛 이름도), 없으면
  만드는 명령을 알린다. `엔진만들기` 는 가중치를 올린 뒤 남은 장치 메모리(cuMemGetInfo)로 할당을 세어 들지 않으면 문맥을 64 씩 줄이고 알린다.
- **고침**: Q4_0 의 층 · 낱말표 · 머리 버퍼의 크기(`Q8바이트`)가 Q8_0 의 값 크기(K · N)로 잡혀 층마다 K · N / 2 바이트가 비었다(값의 자리는
  맞았다 — 커널은 주소 함수를 쓴다). 14B 는 그 때문에 12 GB 에 들지 않았다. 7B Q4_0 은 1.9 GB 를 더 썼다. 고친 뒤 7B Q4_0 의 출력은 23단계와
  바이트까지 같다.
- **합성 모델**(`준비/합성qwen2.py`): 바탕 GGUF(7B)의 메타데이터를 바이트 그대로 옮기고 모양 열쇠만 바꾼 뒤, 형식의 블록을 무작위로(텐서 이름마다
  씨앗) 쓴다. llama.cpp 도 읽는다.

### 밝혀 둘 것

1. **공식 실행의 첫 시도는 24a 뒤에 멈췄다.** 스크립트의 bash 배열 이름을 한글(`새`)로 지어 그 줄에서 문법 오류가 났다(bash 는 한글 변수 이름을
   받지 않는다 — 20 · 22단계에 이어 세 번째로 같은 함정). 이름을 영어(`MODELS`)로 바꾸고 문법 검사(`bash -n`)를 거쳐 빌드부터 처음부터 다시
   돌렸다. 첫 시도의 24a(같음)는 다시 돌린 것과 같다.
2. **Q4_0 버퍼 크기 버그**(위 — 만든 것): 23단계의 7B Q4_0 측정은 1.9 GB 를 더 쓴 상태였다. 출력은 같고, 이 단계의 회귀(7B Q4_0 다섯 길 요약이
   23b 와 바이트까지 같음)로 다시 봤다.
3. **시운전 중 시간을 잘못 읽었다.** 14B 다섯 길 시험(시운전)의 기록 파일이 오래 비어 있어 2100 토큰 경우가 30 분 넘게 걸린다고 보고 시각을
   찍는 판으로 그 경우만 다시 돌렸다(96 초 — 대부분 0.83 GB KV 캐시의 해시 다섯 번). 나중에 파일 시각으로 보니 시운전은 13:18:45 에 시작해
   13:24:51 에 끝났다 — 도구의 표준 출력이 끝날 때 한꺼번에 써져 기록이 비어 보였을 뿐 멈춘 적은 없다. 공식 실행에서도 6 분에 끝났다.
4. **14B 파일은 공식 q4_0 을 다시 양자화했다**(미리 적은 대로): `llama-quantize --allow-requantize --pure` 로 텐서 579 개 중 Q4_0 338 · F32 241,
   8,317,001,056 B(출력 가중치 Q6_K → Q4_0).
5. **합성 모델은 학습한 모델이 아니다**(무작위 가중치, 층 넷). 비트 · 길 · 모양의 일반화를 보이는 데만 쓰고, 속도는 기록이다.
6. **대조 도구는 파이썬이다**(미리 적은 대로).

## 남은 것 (24단계 끝)

- 이 PC 의 12 GB 로는 32B · 72B 를 실제로 돌릴 수 없다 — 층 나누기(25단계)로 여러 GPU 에, 또는 한 GPU 에서 흉내 내어 길을 만든다.
- 프롬프트는 1.2 ~ 1.6 배다(묶음 어텐션 · Q4_0 타일의 니블 풀기). 생성은 바닥의 1.15 배(14B Q4_0) — 층을 묶는 생성 메가커널이 다음 수다.
- 다섯 길 시험의 KV 해시(글로 쓴 SHA-256, 초당 약 50 MB)가 큰 모델에서 시험 시간의 대부분이다.
