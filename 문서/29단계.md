# 29단계 — 리눅스: 같은 GPU, 같은 비트 (2026-10-12)

지금까지 GeulPU 는 윈도에서만 돌았다. 엔진 · 호스트 · 커널 생성기가 글(geul) 언어로 쓰여 있는데, 글 컴파일러가 윈도 실행 파일(PE)만
냈기 때문이다. 글 저장소의 D-50 이 리눅스 x86-64 대상을 더했다(ELF, 바깥 함수와 함수 값의 호출은 System V, 운영체제의 바닥은 libc).
이 단계는 GeulPU 의 체계층(운영체제와 닿는 자리 — 파일 사상 · 스레드 · 소켓 · CUDA 드라이버의 이름)을 리눅스로 옮기고, 같은 코드가
리눅스에서도 같은 GPU 에서 **같은 비트**를 내는 것을 보인다.

28단계 끝에 적은 차례(29단계 함께 걷는 걸음 · MoE · 리눅스)를 사용자의 결정으로 바꿨다. 함께 걷는 걸음은 30단계로 미룬다.

시험 환경은 이 PC 의 WSL2 Ubuntu 24.04(커널 6.18.33.2-microsoft-standard-WSL2, glibc 2.39)이고, GPU 는 윈도와 같은 RTX 4070 Ti 다.
WSL 의 `libcuda.so.1` 은 윈도의 그래픽 드라이버(616.56)와 함께 오는 리눅스 판이다(`/usr/lib/wsl/lib`, 드라이버 API 판 13.4).

판정 기준을 결과보다 먼저 적는다.

## 진단 (이 문서보다 먼저 — GeulPU 의 코드는 아직 바뀌지 않았다)

- **글로 만든 ELF 가 libcuda 를 부른다.** 리눅스 대상으로 컴파일한 작은 탐침(바깥 선언 다섯)이 WSL 에서 cuInit · cuDeviceGet ·
  cuDeviceGetName · cuDeviceGetAttribute · cuDriverGetVersion 을 불러 "NVIDIA GeForce RTX 4070 Ti", SM 60, 13040 을 냈다.
- **모델 파일.** WSL 에서 윈도 디스크(`/mnt/c`, 9P)의 GGUF 를 mmap 으로 처음부터 끝까지 읽으면 0.20 GB/초(0.5B Q8_0 0.68 GB) ·
  0.34 GB/초(7B Q4_0 의 앞 2 GB)다. 비트 대조에는 그대로 쓰고, 올림 시간은 판정이 아니라 기록으로 둔다.
- **글 컴파일러.** 글 저장소 `feat/linux`(f638373 — D-50)를 `research/gpu` 에 병합했다(39b4bb1, 충돌 없음). 이 병합의 트리로 윈도에서:
  수용 216/216 · 핫스왑 143/143 · 자체 컴파일러의 수용 216/216, 덤프 177×3 · 실행 파일 147 · 교차(리눅스 ELF) 149 의 바이트가 두
  구현에서 같고, 고정점(542,208 B). GeulPU 빠른 점검 — 모듈 여섯의 소스 · PTX 가 `시험/모듈해시.txt` 와 같고, 프로그램 19 개가
  빌드되고, 가져오기 표가 그대로다.

## 무엇을 만드나

### 1. 체계층을 가른다

리눅스 대상이면 글 컴파일러는 `D/X.gl` 대신 `D/리눅스/X.gl` 을 포함한다(글 명세 3.1). 그래서 운영체제와 닿는 코드만 파일로 떼어 내고, 그
리눅스 판을 `호스트/리눅스/` 에 둔다. 이름 · 매개변수 · 역할 · 반환 타입은 두 판에서 같다.

| 파일 | 윈도 | 리눅스 (`호스트/리눅스/`) |
|---|---|---|
| `쿠다선언.gl` (`쿠다.gl` 에서 바깥 선언만 떼어 낸다) | `nvcuda.dll` | `libcuda.so.1` — 같은 기호 · 같은 서명 |
| `파일.gl` | CreateFileW · ReadFile · WriteFile · CreateFileMappingW · MapViewOfFile | open · read · write · fstat · mmap · munmap (사상풀기에 쓸 길이를 기억해 둔다) |
| `스레드.gl` | CreateThread(스택 8 MB) · WaitForSingleObject · GetActiveProcessorCount | pthread_create(스택 8 MB) · pthread_join · sysconf |
| `소켓체계.gl` (`소켓.gl` 에서 체계층만 떼어 낸다) | ws2_32 · WSAPoll | BSD 소켓 · poll, SIGPIPE 무시, 듣는 소켓에 SO_REUSEADDR |

- 서버가 WSAPOLLFD 의 꼴(칸마다 16 바이트)을 직접 다루던 것을 소켓체계의 함수(살핌넣기 · 살핌결과 · 살핌판만들기)와 소켓오류 ·
  막힘오류로 옮긴다(리눅스의 pollfd 는 8 바이트).
- 실행기 · 서버의 "이 실행 파일의 폴더": GetModuleFileNameW 대신 글 표준 라이브러리의 `실행파일_경로()`(D-50).
- 커널 생성기의 통째쓰기: 자기 kernel32 선언 대신 `호스트/파일.gl` 을 포함한다.
- 계산(커널 소스 · PTX · 엔진의 셈 · 뽑기 · 서버의 HTTP)은 한 글자도 운영체제에 따라 갈리지 않는다.

### 2. 도구

- `시험/빠른점검.py` 가 리눅스에서도 돈다 — 실행 파일은 확장자 없는 ELF, 가져오기 검사는 DT_NEEDED(실행기 · 서버는 `libc.so.6` ·
  `libcuda.so.1` 뿐).
- CI 에 리눅스 작업(ubuntu)을 더한다 — 참조 구현 → 자체 컴파일러 → PTX 뒷단을 리눅스에서 만들고, 모듈을 처음부터 만들어 해시를 견준다.
  `시험/글저장소커밋.txt` 를 병합 커밋으로 옮긴다.
- 공식 실행 `공식실행/공식29.sh` — WSL 안에서 돈다. 입력 파일(`시험/입력7B.py` · `공식실행/입력18d.py` — 뒤의 것은 numpy 가 든다)은
  윈도의 파이썬으로 만든 것을 그대로 쓴다(두 운영체제가 같은 바이트의 입력을 받는다). 서버의 하네스 `시험/서버28.py` 는 표준 라이브러리만
  쓰므로 WSL 의 파이썬으로 돈다.

## 판정 (미리 정함)

**29a 빌드.** 리눅스(WSL)에서:

- 글 저장소(병합 커밋)의 참조 구현으로 자체 컴파일러를 만들고, 그것이 자기 자신을 두 번 더 컴파일해 세 세대가 같은 바이트다.
- 그 컴파일러로 PTX 뒷단 · 커널 생성기 · 호스트 프로그램 전부(빠른점검이 빌드하는 것)를 ELF 로 만든다. C 컴파일러 · 링커는 쓰지 않는다.
- 실행기 · 서버의 DT_NEEDED 는 `libc.so.6` · `libcuda.so.1` 뿐이다.

**29b 모듈.** 리눅스에서 만든 모듈(커널 소스 · PTX)이 `시험/모듈해시.txt`(윈도에서 만든 것)와 바이트까지 같다 — 표의 모듈 여섯 모두.

**29c 같은 비트.** WSL2 · 같은 RTX 4070 Ti 에서 시험_7B 의 다섯 길 요약이 윈도의 기록과 바이트까지 같다:

- 7B Q8_0 · Q4_0 → `문서/결과/23단계/23b_요약_Q8.txt` · `23b_요약_Q4.txt`
- 14B Q4_0 → `문서/결과/24단계/24c_요약_14b-q4_0.txt`
- 7B Q4_K_M · Q5_K_M · Q6_K → `문서/결과/26단계/26b_요약_q4_k_m.txt` · `26b_요약_q5_k_m.txt` · `26b_요약_q6_k.txt`
- 0.5B 의 18d 출력(시험_엔진) → `문서/결과/18단계/18d_엔진_글.txt`

입력은 28e(2)와 같은 `공식입력7B.bin` · `18d입력.bin` 이다. 일곱 모두 같아야 한다.

**29d 서버.** 리눅스에서 서버(7B Q4_0, 슬롯 4 · 문맥 4096)를 띄워:

- (1) 28c 의 열셋이 모두 맞는다.
- (2) 28a 의 요청 모음 · 차례 넷((가) ~ (라))을 같은 하네스(`시험/서버28.py`)로 돌린다. 요청마다 생성 토큰과 걸음마다의 로짓 해시가
  윈도의 28a 기록(`문서/결과/28단계/28a_q4_0.json`)과 같다 — 다른 것 0.

**29e 윈도 그대로.** 체계층을 가른 뒤 윈도에서:

- (1) 빠른점검이 통과한다(모듈 해시 그대로).
- (2) 29c 의 일곱이 기록과 바이트까지 같다.
- (3) 29d 의 (1) · (2)가 윈도의 서버에서도 맞는다.

판정이 아닌 기록:

- 7B Q4_0 의 생성 · 프롬프트 시간(재기_7B)과 서버 한 · 넷 스트림의 걸음 — 리눅스(WSL)와 윈도. WSL 의 GPU 길(윈도의 dxgkrnl 을 거친다)이
  끼므로 네이티브 리눅스의 속도가 아니다.
- 모델 올림 시간(WSL 은 `/mnt/c` 의 9P).

### 하지 않는 것

- 네이티브 리눅스(실제 리눅스 컴퓨터). 이 PC 에는 WSL2 뿐이다. 같은 ELF 가 네이티브 리눅스 · NVIDIA 드라이버에서도 돌 것이라 기대하지만
  이 단계는 보이지 않는다.
- ARM64 · macOS(글 컴파일러에 대상이 없다).
- 속도 고치기(WSL 의 덧비용 줄이기), 글 1.4.0 판 내기 · 리눅스 배포물(사용자의 승인 뒤).

### 미리 밝혀 둘 것

1. **이 문서보다 먼저 한 것**은 위의 진단과 글 저장소의 일(D-50 리눅스 대상, research/gpu 병합)이다. GeulPU 의 코드는 아직 바뀌지 않았다.
2. 29c · 29d 의 견줄 것은 윈도에서 이미 남긴 기록 파일이다. 29e 가 윈도에서 지금도 그 기록이 나오는지 따로 본다.
3. WSL 의 PTX JIT(드라이버가 PTX 를 SASS 로 바꾸는 것)은 `libcuda.so.1` 안에 있고, 윈도의 nvcuda.dll 의 것과 같은 판인지는 모른다.
   GeulPU 의 PTX 는 셈의 반올림을 모두 밝혀 적어(.rn — 계약) JIT 이 셈을 바꿀 자리가 없게 했다. 그래서 같은 비트가 나와야 하고, 29c 가
   그것을 본다.
4. 모델은 윈도 디스크(`/mnt/c`)에서 읽는다(진단의 속도).
