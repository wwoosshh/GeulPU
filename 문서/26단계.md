# 26단계 — k-양자화(Q4_K · Q5_K · Q6_K)를 계약 안에: 사람들이 받는 GGUF 그대로 (2026-10-12)

추천 순서의 (4) "k-양자화 · MoE · 서버 기능" 의 첫 단계다. 사람들이 받아 쓰는 GGUF 는 대부분 k-양자화(Q4_K_M · Q5_K_M · Q6_K)다 — 공식
Qwen2.5 GGUF 도 그렇다. 지금 엔진은 모델 하나에 형식 하나(Q8_0 또는 Q4_0)만 받는다. 이 단계에서 k-양자화의 형식 셋을 정수 계약에 넣고,
텐서마다 형식이 다른 GGUF(섞음)를 그대로 돌린다. **시험은 이 PC 안에서만** 한다. 앞의 계약 손실 검토(문서/계약손실검토.md)는 계약을 고칠
까닭을 찾지 못했다 — 계약의 활성값 쪽은 그대로 두고 가중치 쪽에 형식을 더한다.

판정 기준을 결과보다 먼저 적는다.

## 무엇을 만드나

1. **계약(문서/계약.md 1절)에 k-양자화 셋.** 가중치는 파일의 정수와 척도 그대로 쓴다. 활성값의 32 칸 블록과 자리 둘(n = 256·D₁ + D₀)은 지금과 같다.
   - **Q4_K · Q5_K** (슈퍼블록 256 = 32 칸 아래블록 여덟, 반실수 d · m, 아래블록마다 6비트 s_j · t_j — llama.cpp 의 get_scale_min_k4 와 같은 풀기,
     q ∈ [0, 15] · [0, 31]): a_j = d · s_j, b_j = m · t_j (둘 다 짧은실수로 정확). 활성값 블록 j(= 아래블록 j)마다 S_j = Σ_k n_k · q_k,
     T_j = Σ_k n_k (정확한 정수 — |S| < 2²⁴), u_j = S_j · 2^(E−13), w_j = T_j · 2^(E−13) (정확). j 오름차순으로 사슬 하나:
     **y ← 곱해더하기(u_j, a_j, y), y ← 곱해더하기(−w_j, b_j, y)**, 출력 = y + 치우침. (사슬이 하나면 타일 판의 누산 레지스터가 늘지 않는다.)
   - **Q6_K** (슈퍼블록 256 = 16 칸 아래블록 열여섯, 반실수 d, 아래블록마다 부호 있는 8비트 s_k, q ∈ [0, 63]): a_k = d · s_k (정확). 아래블록
     k 마다 S_k = Σ n · (q − 32) (16 칸, 정확 — |S| ≤ 2²³), u = S_k · 2^(E−13), **y ← 곱해더하기(u, a_k, y)** 를 k 오름차순으로.
   - 임베딩(낱말표가 k-양자화일 때): Q4_K · Q5_K 는 a_j · q − b_j (곱은 정확, 뺄셈에서 반올림 하나), Q6_K 는 a_k · (q − 32) (정확).
   - Q8_0 · Q4_0 의 식은 그대로다(1절 4). CPU 참조는 `계약/정수계약.py` 의 풀기K · 행렬곱K · 행렬곱K블라스 · 임베딩K.
2. **텐서마다 형식.** k-양자화 모델은 층마다 · 행렬마다(q · k · v · o · gate · up · down · 낱말표 · 출력) 형식이 다를 수 있다(Q4_K_M 은 v ·
   down 의 일부 층과 출력이 Q6_K). 엔진은 행렬마다 그 형식의 판을 띄운다. qkv 를 하나로 묶은 행렬에서 형식이 갈리면(q · k 와 v) 형식이 같은
   열 구간마다 따로 띄운다. 받는 것: k-양자화 모델의 행렬은 Q4_K · Q5_K · Q6_K 의 아무 섞음, Q8_0 · Q4_0 만의 모델은 지금 길 그대로.
3. **글 생성기 · 호스트.** 판(타일 판 — 프롬프트, 정수줄하나 · 잔차 · SwiGLU — 생성, 임베딩, 로짓은 머리 형식의 "" 판)에 형식 셋. 엔진의
   배치는 형식마다 [블록][열][바이트] 꼴(낮은 4비트 · 높은 비트 · 슈퍼블록 척을 따로 — 읽는 바이트는 파일과 같다). 모듈은 모양마다 k-양자화
   셋의 판을 모은 `qwen2K_{모양}` 하나(`커널생성 qwen2큰 K …`). 층 나누기(25단계)와 함께 돈다.
4. **파일은 이 PC 에서 만든다.** 가진 7B Q8_0 에서 `llama-quantize --allow-requantize … Q4_K_M | Q5_K_M | Q6_K` (llama.cpp 의 표준 섞음 그대로 —
   `--pure` 가 아니다) → `qwen2.5-7b-instruct-{q4_k_m,q5_k_m,q6_k}-req.gguf`. 글과 llama.cpp 가 같은 파일을 쓴다.

### 미리 밝혀 둘 것

1. **k-양자화 파일은 이 PC 에서 Q8_0 을 다시 양자화해 만든다**(공식 파일은 bf16 에서 만든다 — 값이 조금 다르다). 섞음(텐서마다의 형식)은
   llama.cpp 의 규칙 그대로라 공식 파일과 같다. 두 엔진이 같은 파일을 쓰므로 견주기는 공정하다. 정확도는 판정이 아니다.
2. **이 문서보다 먼저 쓴 것**: 2026-10-11 에 파일 셋을 만들었고, CPU 참조(풀기K · 행렬곱K …)와 생성기 · 호스트 코드의 첫 판을 썼다(커밋하지 않음).
   그때 돌린 것은 CPU 쪽 자체 시험뿐이다 — 느린 참조 대 BLAS 참조(다른 칸 0), 파일의 값 대 Q8_0 의 상대 RMS(Q4_K 0.075 · Q5_K 0.04 · Q6_K 0.02 —
   풀기가 맞는지). GPU 판의 대조 · 시간은 이 문서를 커밋한 뒤에 한다.
3. Q2_K · Q3_K · IQ 계열 · Q5_0 은 이 단계에 없다. 실제 72B 의 k-양자화 파일은 ffn_down(깊이 29568 — 256 의 배수가 아니다)을 Q5_0 · Q8_0 으로
   두므로 이 단계로는 돌지 않는다(7B · 14B · 32B 는 모든 깊이가 256 의 배수).
4. Q6_K 의 타일 판은 아래블록(16 칸)마다 합이 따로 들어 정수텐서곱(k32)을 B 의 반을 가려 두 번 한다 — 프롬프트에서 Q6_K 의 정수 텐서 일은 두 배다.
5. **대조 도구는 파이썬이다**(CPU 참조 · 견주기). 엔진 · 생성기 · 실행기는 글이다.
