연구는 글 저장소의 `research/gpu` 가지에서 했다. 단계마다 판정 기준을 실험보다 먼저 적고(커밋으로 남김), 모든 변형을 비트 대조한 뒤에

## 남은 것 (23단계 끝)

- 7B 생성은 llama.cpp 의 0.97 ~ 0.99 배지만 바닥(504 GB/s)의 1.11 배(Q8_0) · 1.16 배(Q4_0)다. 블록이 적은 행렬곱(qkv · o — 368 ~ 420 GB/s),
  층마다의 작은 커널 다섯(RMS 둘 · RoPEKV · 어텐션 · 접기 — 짧은 문맥에서 토큰당 약 0.45 ms), 8192 의 어텐션(1.24 ms)이 남은 곳이다 —
  층을 한 커널로 묶는 7B 생성 메가커널.
- 프롬프트는 이 단계에서 손대지 않았다: Q4_0 1.23 · 1.38 배, Q8_0 1.15 · 1.30 배.
- 다음: 설정에서 모델 모양(14B · 32B · 72B), 층 나누기 다중 GPU, k-양자화 · MoE · 서버 기능.

## 남은 것 (22단계 끝)

- 7B 의 생성: llama.cpp 의 1.05 ~ 1.07 배(바닥 504 GB/s 의 1.19 ~ 1.21 배 — llama.cpp 1.12 ~ 1.13 배). 블록이 적은 줄 판(qkv · o · down 이 대역폭의
  75 ~ 90%), 층마다의 RMS 띄움, 긴 문맥의 조각 어텐션(8192 에서 1.7 ms)이 남은 곳이다. 채팅에서는 끝 토큰 뒤의 걸음(답마다 많게는 15 걸음)을
  장치에서 멈추게 할 일이 있다.
- 7B 의 프롬프트: 1.14 배(2048) · 1.30 배(8192). 머리 128 의 묶음 어텐션이 첫 판이다(넘침 384 B — 8192 에서 시간의 28%, 자리 둘 × 자리 둘의 바닥의
  2.9 배). 행렬곱은 21단계 그대로다.
- 실행기의 판 고르기(7B 약 3.6 초)를 파일에 두기.

## 남은 것 (21단계 끝)

- 22단계: 7B 전체 — 머리 128 의 어텐션(점수 눈금 1/√128 의 반올림을 계약에, RoPE 표 64 칸), QKV 끝손질, 생성 길, 호스트의 7B 크기.
  그리고 큰 행렬곱의 블록 차례(그룹 래스터) 또는 덩이 나누기로 8192 의 L2 틈을 메운다.
- 글 퍼플렉시티 도구는 llama-perplexity 보다 느리다(70 ~ 81 초 대 16 ~ 52 초 — 로짓 155 MB 를 CPU 로 받고 fp64 NLL 을 CPU 에서). GPU 에서
  로그 확률을 세면 줄일 수 있다.

## 남은 것 (19단계 끝)

- Qwen2 채팅은 빌드도 실행도 글 컴파일러와 nvcuda.dll 만으로 된다. 글 배포판(1.2.1)의 `geulc.exe` 로 빌드해도 같은 바이트다. 단, 자체 호스팅
  컴파일러를 소스에서 처음 만드는 1세대는 파이썬 참조 구현이 만든다(씨앗).
- 남은 파이썬(Qwen2 채팅의 빌드 · 실행에는 들지 않는다): GPT-2 의 모듈 22 개와 파이썬 연구 엔진(`엔진/` · `커널모듈.py` · `커널생성.py`), 대조용
  파이썬 호스트(`실행.py`) · 파이썬판 PTX 컴파일러, 정답지 · 시험 · 재기.
- 다음 후보: 더 많은 모델 모양(머리 128 · 다른 크기 — 생성기가 글이 되었으니 설정을 넓히는 일도 글에서), k-양자화, 샘플링.

## 남은 것 (18단계 끝)

- 실행에는 파이썬이 들지 않는다. 남은 파이썬: 커널 소스(글)를 만드는 생성기 `커널/커널생성.py` 와 그것을 글 PTX 뒷단에 넘기는 `엔진/커널모듈.py`
  — 19단계에서 글로(그러면 빌드도 "글 컴파일러 + nvcuda.dll" 만으로). 그리고 대조 · 재기 도구.
- ~~모델을 올리는 시간이 파이썬 호스트보다 길다(3.1 대 2.9 초)~~ — 18단계 뒤에 고쳤다: RoPE 빠른 길 · 판 고르기 데우기 · GGUF 사상 · 일꾼 스레드로
  프롬프트까지 0.24 ~ 0.29 초, 값은 모두 같다([18단계](18단계.md) 의 '18단계 뒤').

## 남은 것 (17단계 끝)

- GPU 코드(PTX)는 글 컴파일러가 낸다. 아직 파이썬인 것: 커널 소스(글)를 만드는 생성기(`커널/커널생성.py`)와 호스트(GGUF 읽기 · 토크나이저 ·
  커널 띄우기 · 실행기), 시험 · 재기 도구. 이것들을 글로 옮겨 "글 실행 파일 하나 + 드라이버" 로.
- 글 PTX 뒷단의 정답지는 아직 파이썬판(바이트 대조)이다 — 엔진의 모듈이 쓰지 않는 꼴(부호 없는 64 비트 정수 등)은 다른 PTX 를 내지 않고 거부한다.
- 15단계 끝의 성능 과제는 그대로다(아래).

## 남은 것 (15단계 끝)

- 생성은 바닥의 1.21배 — 데우는 블록이 장벽이 풀린 것을 늦게 알아차리는 시간(층마다 1~4 µs), 데우기 읽기 뒤의 어텐션 지연, C · D 의 입력 바꾸기를
  블록마다 되풀이하는 몫, 로짓(바닥의 1.07배)이 남았다.
- 이 GPU 에서 미리읽기 명령(prefetch.global.L2 · cp.async)은 L2 에 거의 남지 않는다 — 32 바이트마다 실제로 읽어야 한다(15단계 밝혀 둘 것 2).
- 프롬프트 8192 의 어텐션, 더 많은 모델 모양, k-양자화, 샘플링, Linux. 글 쪽: 네이티브 컴파일러의 PTX 뒷단, 호스트를 글로.

## 남은 것 (14단계 끝)

- 생성은 바닥(가중치 한 번 읽기 1.04 ms)의 1.56배 — 커널 147 개의 띄움 사이와 작은 행렬곱의 지연. 생성 메가커널로.
- 프롬프트 8192 의 어텐션(층마다 3.4 ms)이 가장 큰 몫 — 계약의 산수(적힌지수 · e′ 자리)가 정하는 명령 수.
- 더 많은 모델 모양(머리 128 · 다른 너비), k-양자화, 샘플링, Linux.

## 남은 것 (13단계 끝)

- 문맥 10만 가까이의 생성은 llama.cpp 와 1% 안팎 — 두 엔진 모두 실제 읽기 대역 가까이에 있다(글의 KV 는 지수 바이트만큼 1.6% 크다).
  생성 메가커널의 단계 사이(장벽 · 접는 블록의 꼬리)를 줄여야 한다.
- 타일 효율(int8 최고치의 53%)과 프롬프트 어텐션(바닥의 2.3~2.9배)은 계약의 산수가 정하는 명령 수에 묶여 있다.
- 다음: Llama 계열 블록 세트(RoPE · RMSNorm · SwiGLU · GQA · 머리 128)로 첫 채팅 모델, 터미널 실행기.
