# 28단계 — 서버: 함께 도는 요청과 상관없이 같은 비트 (2026-10-12)

23단계에 적은 차례의 넷째가 서버 기능이다. 로컬 AI 는 대개 서버(llama-server · ollama)로 띄우고, 다른 프로그램이 HTTP 로 부른다. 서버는 요청
여럿을 한 배치로 함께 돌려 처리량을 낸다. 그런데 함께 돈 요청에 따라 답이 바뀌면, 같은 질문의 답이 그때그때 달라진다. 이것이 배치 불변성의
문제다(Thinking Machines 2025, 그리고 vLLM · SGLang 이 속도를 내주고 켜는 batch-invariant 모드가 다루는 것).

GeulPU 의 계약은 행마다의 값이 다른 행과 상관없게 적혀 있다(3b · 4c · 20a). 이 단계는 그 성질을 서버의 끝에서 끝까지, 곧 HTTP 요청에서
응답의 토큰까지 보인다. 그리고 뽑기(샘플링)를 계약으로 적는다. 씨앗이 같으면 몇 개와 함께, 어느 슬롯에서 돌든 같은 토큰이 나와야 한다.
시험은 이 PC 안에서만 한다.

판정 기준을 결과보다 먼저 적는다.

## 진단 (이 문서보다 먼저 — 서버 코드는 아직 없다)

### llama-server 는 함께 돈 요청에 따라 탐욕 답이 바뀐다

처음 다른 글자의 자리다.

## 무엇을 만드나

### 1. 서버 `호스트/서버.gl` (글 언어)

```
서버 모델.gguf [--ptx 경로] [--주소 127.0.0.1] [--포트 8080] [--슬롯 4] [--문맥 4096] [--덩이 512] [--이름 모델이름] [--기록 폴더]
```

- 실행 파일은 글 런타임의 kernel32 · shell32 와 nvcuda.dll, ws2_32.dll(윈도의 소켓)만 가져온다. 스레드는 하나다. 소켓을 막지 않게 두고
  WSAPoll 로 돌보며, GPU 일과 번갈아 한다. 모델 올리기는 실행기와 같다(일꾼 겹치기).
- 받는 모델: 머리 128 의 Qwen2(7B · 14B — Q8_0 · Q4_0 · k-양자화). 0.5B(머리 64)와 층 나누기는 받지 않는다고 알리고 멈춘다.
- HTTP/1.1: Content-Length 의 몸, 연결 이어 쓰기(keep-alive) · `Connection: close`, `Expect: 100-continue`, 흘려보내기는
  `Transfer-Encoding: chunked` 의 SSE, OPTIONS 와 모든 응답에 CORS 머리(`Access-Control-Allow-Origin: *`), 몸은 16 MB 까지.
  TCP_NODELAY 를 켠다.
- 길:
  - `GET /health`
  - `GET /v1/models`
  - `POST /v1/chat/completions`(흘려보내기 · 아님)
  - `POST /v1/completions`(프롬프트는 글 또는 토큰 번호 배열)
- 받는 필드:
  - `messages`(system · user · assistant; content 는 글 또는 `{type: "text"}` 조각 배열), `prompt`
  - `max_tokens`(= `max_completion_tokens`), `temperature`, `top_p`, `seed`, `stop`(글 또는 넷까지의 배열), `stream`,
    `stream_options.include_usage`
  - 덧붙임(llama.cpp 와 같은 이름): `top_k`, `min_p`, `ignore_eos`, `cache_prompt`
  - 시험용 `geulpu`: `logit_hash` 는 걸음마다 로짓 행의 64 비트 해시를, `record` 는 서버를 `--기록` 으로 띄웠을 때 토큰 · 로짓을 파일로 남긴다.
  - 뜻을 바꾸는데 따르지 못하는 필드는 400 으로 거절한다: `n` > 1, `logprobs`, 0 이 아닌 벌점, tools, text 가 아닌 `response_format`.
  - 그 밖의 모르는 필드는 무시한다.
- 응답은 OpenAI 꼴이다(id · object · created · model · choices · usage).
  - 흘려보내기는 `chat.completion.chunk` · `text_completion` 조각과 `data: [DONE]` 으로 한다.
  - 덧붙임 `geulpu` 에 쓴 씨앗 · 생성 토큰 번호(· 해시)를 넣는다. 씨앗을 주지 않은 요청도 받은 씨앗으로 같은 답을 다시 낼 수 있다.
- 채팅 틀: GGUF 에 든 Qwen2.5 의 ChatML. system 이 없으면 기본 시스템 말을 넣는다(실행기의 첫 차례와 같은 토큰).
- 멈춤:
  - 끝 토큰(`<|im_end|>` · `<|endoftext|>` — `ignore_eos` 면 무시)
  - `max_tokens` 와 슬롯 문맥이 차면 `length`
  - stop 글이면 `stop` — 글은 그 앞에서 자르고, 흘려보낼 때는 stop 글의 머리일 수 있는 꼬리를 남겨 둔다
  - UTF-8 이 끊긴 꼬리는 다음 조각으로 미룬다.

### 2. 슬롯 · 연속 배치 · 프롬프트 캐시 (엔진 `호스트/엔진.gl`)

- 슬롯 S 개(`--슬롯`, 1 … 8)는 저마다 KV 캐시 자리(층마다 [슬롯][KV 머리] …)와 지금 캐시에 든 토큰열을 가진다.
  S = 1 이면 장치에 잡는 것이 지금과 같다(실행기 · 시험 · 재기는 S = 1).
- 새 요청은 빈 슬롯 중 캐시 토큰열과 앞이 가장 길게 같은 슬롯에 든다(같으면 작은 번호). 그 앞만큼은 다시 셈하지 않는다. 전부 같으면
  마지막 토큰 하나는 다시 넣어 로짓을 얻는다. `cache_prompt: false` 면 위치 0 부터 넣는다.
- 남은 프롬프트는 덩이(`--덩이`, 기본 512 행)마다 지금의 프롬프트 길(타일 판 · 묶음 어텐션)로 넣는다. KV 주소는 그 슬롯의 것이다.
  덩이 하나와 생성 걸음 하나를 번갈아 한다.
- 생성 걸음: 생성 중인 슬롯 B 개가 한 그래프로 함께 걷는다. 그래프는 B 마다 하나씩 짓는다.
  - 토큰 · 위치 · 슬롯을 장치의 표(한 번 올림)에서 읽는다.
  - 행렬곱의 판:
    - B = 1 은 정수줄하나(지금 생성 그래프의 판)
    - 2 ≤ B ≤ 4 는 정수줄자리
    - B ≥ 5 는 타일 판
    - k-양자화는 B = 1 이 정수줄하나K, B ≥ 2 가 타일 판
  - 어텐션은 새 표 판 셋이 맡는다(아래 3).
  - 걸음마다 다음 토큰(탐욕은 장치의 가장 큰 번호, 뽑기는 그 행의 로짓을 내려 호스트에서 — 아래 4)을 받고 기다린다.
- 요청이 슬롯보다 많으면 줄을 세운다(64 개 넘으면 503). 연결이 끊긴 요청은 슬롯을 놓는다.

지금 판에 `표` 갈래를 더한다.

|---|---|---|

| `정수조각접기넓표` | `정수조각접기넓칸` | 조각 끝을 문장의 위치에서 |

- 문장은 행 / 묶음안행수다(서버는 문장마다 행 하나).

### 4. 뽑기 계약 (문서/계약.md 에 더한다)

들어오는 것:

- 로짓 z ∈ f32^V(엔진이 낸 비트)
- 온도 T(f64 ≥ 0), top_k K(정수 ≥ 0, 0 = 끔), top_p P(f64, 0 < P ≤ 1), min_p Q(f64, 0 ≤ Q < 1)
- 씨앗 s(u64), 걸음 i(요청의 첫 생성 토큰이 0)

셈은 f64 다. 적은 차례로 하나씩 반올림하고, 곱해더하기는 쓰지 않는다.

1. T = 0 또는 K = 1 이면 z 가 가장 큰 번호 중 가장 작은 것을 고른다(장치의 가장큰번호와 같은 뜻).
2. 번호를 (z 내림차순, 같으면 번호 오름차순)으로 늘어놓는다: j₁, j₂, …
3. a_k = (f64(z_{j_k}) − f64(z_{j₁})) / T 로 둔다. 빼기는 정확하고, 나누기에서 한 번 반올림한다. 후보는 a_k ≥ −40 인 앞부분(길이 n_F)이다.
   **밝힌 손실**: 가장 큰 것의 e⁻⁴⁰ ≈ 4 × 10⁻¹⁸ 배보다 작은 확률은 0 으로 둔다.
4. n_K = K > 0 이면 min(K, n_F), 아니면 n_F 다.
5. 무게 w_k = 지수(a_k) 를 k ≤ n_K 에서 구한다(w₁ = 1). 누적 c_k = c_{k−1} + w_k 를 차례로 더한다(c₀ = 0).
6. top-p: P < 1 이면 n_P 는 c_k ≥ P × c_{n_K} 인 가장 작은 k 다. 아니면 n_P = n_K 다.
7. min-p: n_Q 는 w_k ≥ Q 인 k(≤ n_K)의 수다(w 는 늘어놓은 차례로 줄어든다 — 앞부분).
8. n = min(n_P, n_Q) 로 둔다(≥ 1).
9. u = (분할섞기64(s, i) ≫ 11) × 2⁻⁵³, t = u × c_n 으로 둔다. c_k > t 인 가장 작은 k(≤ n)의 j_k 를 고른다. 없으면(반올림) j_n 이다.

함수 둘:

- 분할섞기64(s, i): x = s + (i + 1) · 0x9E3779B97F4A7C15 (mod 2⁶⁴) 로 시작해 차례로
  x ← (x ⊕ (x ≫ 30)) · 0xBF58476D1CE4E5B9, x ← (x ⊕ (x ≫ 27)) · 0x94D049BB133111EB, x ← x ⊕ (x ≫ 31) 을 한다. ≫ 는 부호 없는 밀기다.
  SplitMix64 를 s 로 시작했을 때의 (i + 1) 번째 값과 같다.
- 지수(a), a ∈ [−40, 0]:
  - k = ⌊a × 1.4426950408889634 + 0.5⌋
  - r = (a − k × 0x1.62e42feep−1) − k × 0x1.a39ef35793c76p−33 (fdlibm 의 ln2 높은 · 낮은 쪽)
  - p ← 1/13!, p ← p × r + 1/n! (n = 12, 11, …, 0). 1/n! 은 f64(1) / f64(n!) — n! ≤ 13! 은 f64 로 정확하다.
  - 값은 p × 2^k(2^k 는 비트로 만들어 곱한다 — 정확).

기본값(요청에 없을 때)은 llama-server 와 같다: T 0.8, K 40, P 0.95, Q 0.05. 씨앗이 없으면 시각에서 하나를 뽑아 응답에 넣는다. 뜻은
llama-server 와 다르다. llama.cpp 는 top-k · top-p · min-p 를 온도 1 의 확률로 자르고 온도를 마지막에 쓰는데, 이 계약은 온도를 먼저 쓴다
(Hugging Face 와 같은 차례).

이 계약으로 고른 토큰은 (그 행의 로짓, 매개변수, 씨앗, 걸음)에만 달려 있다. 로짓이 배치와 상관없으면 뽑기도 배치와 상관없다.

**28a 비트 — 함께 돌아도 같다.** — 상태: **통과**

- 요청 모음은 열둘이다: 채팅 탐욕 넷, 채팅 뽑기 다섯(씨앗 · 온도 · K · P · Q 를 달리 — 같은 질문에 씨앗만 다른 둘 포함), 토큰 프롬프트
  탐욕 둘(`/v1/completions` — 끝 무시 64 토큰), 두 차례 대화 하나. 모음은 `시험/서버28.py` 에 두고 공식 실행 전에 커밋한다.
- 차례 넷:
  - (가) 슬롯 1 에 하나씩
  - (나) 슬롯 S 에 모두 한꺼번에
  - (다) 슬롯 S 에 거꾸로, 씨앗을 둔 무작위 틈(0 ~ 2 초)을 두고
  - (라) 슬롯 S 에 요청마다 둘씩(같은 것 둘), 모두 한꺼번에
- 통과:
  - 요청마다 생성 토큰과 걸음마다의 로짓 해시가 (가) ~ (라)에서 모두 같다.
  - (마) 토큰 프롬프트 요청의 걸음마다 로짓이 `시험_7B` 의 한 번에 길(같은 토큰, 22a · 23a 에서 CPU 참조와 대조한 길)의 해당 행과
    비트까지 같다.
  - (바) 둘째 차례가 프롬프트 캐시를 쓸 때와 `cache_prompt: false` 일 때 같다.
  - 네 모델 모두에서 다른 것이 0 이어야 한다.

- (1) 글 뽑기 모듈을 시험 프로그램(`시험_뽑기`)으로 돌려 파이썬 계약판(`시험/뽑기.py`)과 다른 토큰 0. 견주는 것은 합성 로짓 행

### 하지 않는 것

- 행 여럿을 한 번 읽기로 다루는 줄 판. 29단계에서 넷 · 여덟 스트림의 걸음을 llama-server 보다 짧게 하는 것을 목표로 둔다.

### 미리 밝혀 둘 것

1. **이 문서보다 먼저 한 것은 진단뿐이다.**
   - llama-server 의 처리량과 함께 돈 답 견주기 — 하네스 두 개는 표준 라이브러리 파이썬이고, 공식 실행 전에 저장소(`재기/서버재기28.py`)로
     옮긴다.
   - `호스트/재기_줄28.gl` — 있는 판만으로 잰 행렬곱 몫.
   - 서버 · 뽑기 · 표 판의 코드는 아직 없다.
2. llama-server 는 한글 경로의 GGUF 를 열지 못한다. 그래서 같은 파일의 ASCII 경로 하드 링크로 띄웠다(바이트가 같은 파일).
3. 28d 의 기준은 진단에서 낸 셈보다 낮게 잡았다. 넷 스트림은 행렬곱 12.7 ms + 어텐션으로 약 13.5 ms 를 셈해 2.7 배쯤이다. 여덟은 타일 판
   15 ms 대로 4.5 배쯤이다. llama-server 와의 견줌(넷에서 3.4 배)은 판정이 아니라 기록으로 두고, 29단계의 목표로 넘긴다.
4. 뽑기의 기본값은 llama-server 를 따랐다. 그러나 차례(온도를 먼저)는 다르다 — 위 4.
5. 프롬프트 덩이 크기 · 슬롯 수 · 함께 걷는 행 수는 시간만 바꾸고 값은 바꾸지 않아야 한다. 28a 가 그것을 본다.
