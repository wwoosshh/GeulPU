# 38단계 — 연구자 패널: 잡음 없는 관찰 · 개입 · 비교 (사전 등록 2026-10-15)

사용자(2026-10-15): GeulPU 의 존재 의의이자 가장 큰 주장은, LLM 연구자에게 정밀도를 **계약으로 적어** 분석과 추적이 가능한 사실상 유일한
엔진이라는 것이다. 그런데 지금의 로컬 웹 화면은 다른 엔진과 거의 같아 "ollama · LM Studio 와 무엇이 다른가?"에 답하지 못한다. 연구자가
의미 있어 하는 정보를 보여 주는, **실제 연구에 쓸 만한 유일한 매체**가 되게 한다.

첫 초안(지문 · 다시 돌리기 · 배치 보기 · 출처)은 버렸다. 그것들은 "GeulPU 는 재현된다"를 **증명**하는 정보이지, 연구에 **쓰는** 정보가
아니었다. 판정 기준을 결과보다 먼저 적는다.

## 연구자에게 비트까지 같은 것이 왜 필요한가

비트까지 같음이 필요한 곳은 **바꾼 것 하나의 효과를 떼어 볼 때**다 — 엔진 · 모델 이식의 디버깅, 양자화 · 커널 · 추측 디코딩을 바꾼 효과,
강화학습에서 뽑기와 학습이 같은 정책을 보는지, 평가의 회귀 시험([정리 글](https://hidekazu-konishi.com/entry/reproducible_llm_inference.html)).
잡음이 있으면 두 실행의 차이가 바꾼 것 때문인지 셈의 흔들림 때문인지 가를 수 없다.

다른 곳의 현황(2026-10 조사):

- vLLM 의 [배치 불변](https://docs.vllm.ai/en/latest/features/batch_invariance/) · SGLang 의 [결정 모드](https://docs.sglang.io/advanced_features/deterministic_inference.html) —
  같은 GPU · 같은 판 안에서 배치에 따른 흔들림을 없앤다. 판 · 하드웨어가 바뀌어도 같다는 보장은 없고, 이 모드가 아닐 때는 배치가 1 이어도
  접두사 캐시 · 나눠 넣기(chunked prefill)에 따라 결과가 바뀔 수 있다.
- EigenAI([논문](https://arxiv.org/abs/2602.00182)) — 고정한 GPU 구조 위의 비트 재현으로 검증한다(다시 돌려 바이트 비교).
- GPU 세대를 건너는 비트 재현은 연구 중이다 — A100 · L40S 사이 위치의 98.4 % 가 비트까지 같고 H100 과는 9.6 %
  ([preprint](https://arxiv.org/abs/2609.25624)). 제조사(NVIDIA · AMD)를 건너 같다는 결과는 찾지 못했다.

GeulPU 는 계약 덕분에 배치 · 나눠 넣기 · 캐시 · 슬롯이 달라도, GPU · 백엔드 · 제조사(CUDA · Vulkan — NVIDIA · Intel · AMD)가 달라도
같은 비트이고, CPU 참조 구현(적힌 명세)과 비트까지 같다(14 · 22 · 26 · 31 · 34 · 37단계). 그래서 **두 실행의 차이는 연구자가 바꾼 것에서만
나온다.** 이 단계는 이 성질을 연구의 도구로 만든다 — 패널은 상태판이 아니라 **실험대**다: 관찰 · 개입 · 비교 · 기록. 같은 값을 API 와
파이썬으로도 받는다(연구는 대부분 코드로 한다).

## 무엇을 만드나

### 1. 서버 — 로그확률과 점수 (커널 · 생성기는 그대로)

1. **계약 5.2 로그확률**(새로 적음). 로짓 행 z(엔진의 float32 V 개)에서, 모든 셈을 f64 로 적은 차례대로(곱해더하기 없음):
   a_j = f64(z_j) − f64(max z) · S = 어휘를 고정된 16 구간으로 나눠 구간마다 a_j ≥ −40 인 exp_w(a_j)(5절의 exp)를 번호 차례로 더하고,
   구간 합을 구간 차례로 더함 · **logprob_j = a_j − log_w(S)**(log_w = 적힌 로그 — fdlibm 의 log 를 비트로 정한 상수와 차례로) ·
   엔트로피 H = log_w(S) − (같은 구간 차례의 Σ exp_w(a_j) · a_j) / S. 모델의 분포(온도 1 · 거르기 없음)다 — 뽑기의 분포가 아니다.
   e⁻⁴⁰ 아래는 S 에서 빠진다(5절과 같은 밝힌 손실). 상위 k 는 (z 내림차순, 같으면 번호 오름차순).
2. **`/v1/completions`**: `logprobs`(0 ~ 20) · `echo`(프롬프트 토큰의 로그확률까지 — 프롬프트를 조각으로 나눠 조각마다 모든 행의 로짓을
   셈) · 점수만 매기는 `max_tokens: 0`. OpenAI 의 꼴(`tokens` · `token_logprobs` · `top_logprobs` · `text_offset`).
3. **`/v1/chat/completions`**: `logprobs` · `top_logprobs`(OpenAI 의 꼴 — `token` · `bytes`).
4. **`geulpu` 덧붙임**: 프롬프트 토큰 번호(`prompt_tokens`), 걸음마다 엔트로피, echo 행의 로짓 해시.
5. **토큰화**: `/tokenizer_info` · `/tokenize` · `/detokenize`(vLLM 과 같은 꼴 — lm-evaluation-harness 의 원격 토크나이저가 이것으로 돈다).
   관리자가 이 셋도 서버로 넘긴다.

로그확률은 호스트(CPU)가 셈한다 — 커널 · 생성기 · 뒷단은 한 바이트도 바뀌지 않는다. 서버 바이너리는 바뀌므로 R1 교차검증을 다시 돌리고
expected.json 의 서버 해시를 다시 적는다(생성의 글 · 토큰 · 로짓은 같아야 한다).

### 2. 패널 — 실험대 (채팅 오른쪽 · 좁은 창에서는 덮개)

같은 글을 다시 셈하면 생성할 때와 같은 확률이 나온다(계약 — 프롬프트 길과 생성 길이 같은 비트, 38b 에서 확인). 그래서 패널은 채팅
중에는 아무것도 더 셈하지 않고, **들여다볼 때만** 그 답을 점수 매기기(echo)로 다시 셈한다 — 채팅 속도는 그대로다.

1. **관찰**: 답을 토큰으로 — 토큰마다 확률 · 순위 · 대안 상위 k(확률) · 엔트로피 · 1위와 2위의 차(여유). **아슬아슬한 걸음**(여유 < δ —
   셈이나 설정이 조금만 달라도 다른 토큰이 될 자리)과 **1위가 아닌 토큰을 뽑은 걸음** 표시. 답의 요약: 평균 로그확률 · 퍼플렉서티 ·
   가장 작은 여유 · 아슬아슬한 걸음 수.
2. **개입**: 어느 걸음에서 대안 토큰을 골라 **거기서 갈래**(같은 설정으로 이어 생성 — 갈래는 답의 버전으로 남는다), 프롬프트 · 씨앗 ·
   온도를 바꿔 다시.
3. **비교**: 두 답(버전 · 갈래)을 맞대어 처음 갈린 걸음, 토큰마다 로그확률의 차. **같은 글을 다른 모델로 점수** — 예: 같은 모델의
   Q8_0 과 Q4_K_M → 토큰마다의 차는 양자화 하나의 효과다(셈의 잡음이 섞이지 않는다).
4. **점수**: 글을 붙여 넣으면 지금 모델 · 대화 맥락에서 토큰마다 로그확률 · 퍼플렉서티.
5. **재현**: 토큰 · 로짓 지문(SHA-256 — 꼴은 문서에), 재현 캡슐(요청 · 프롬프트 토큰 · 결과 · 로그확률 · 로짓 해시 · 만든 곳)
   내보내기 · 불러와 확인(이 PC 에서 점수 매기기로 견줌), 출처(관리자 `GET /api/provenance` — 엔진 바이너리 · 커널 모듈 · 모델 파일의
   SHA-256, 교차검증 기준 빌드와 같은가), 기준 PC 대조(최근 재현성 검증), 하드웨어 한계(최근 진단).
6. **내보내기**: 보이는 것 모두 JSON · CSV, 그리고 같은 값을 받는 파이썬 코드(OpenAI 클라이언트 그대로).
7. 두 언어(한국어 · 영어).

### 3. 연구자가 이미 쓰는 도구에 붙이기

1. **lm-evaluation-harness**: `local-completions` + 원격 토크나이저로 GeulPU 에 그대로 붙는다(Hugging Face 토크나이저를 받지 않는다).
   README 에 쓰는 법.
2. **`도구/캡슐확인.py`**(파이썬): 캡슐을 **GPU 없이** CPU 참조 구현(계약)으로 다시 셈해 토큰 · 걸음마다 로짓 해시 · 로그확률이 같은지
   본다 — 받는 사람이 GeulPU 를 쓰지 않아도 명세로 비트를 확인하는 길.

### 미리 밝혀 둘 것

1. **계약에 더하는 것은 로그확률의 정의(5.2) 하나**다. 로짓은 이미 계약으로 정해져 있었고(1 ~ 4절), 로그확률 · 엔트로피는 그 위에서 CPU 가
   f64 로 셈한다. 정의가 적혀 있으니 다른 PC · 다른 구현(파이썬)도 같은 비트를 낸다.
2. 로그확률은 **모델의 분포**(온도 1)다. 온도 · top-k · top-p 를 쓴 뽑기의 분포와 다르다 — 화면에 적는다.
3. '정확함'은 **계약 기준**이다 — 양자화한 파일을 계약대로 셈한 값이지, 원본(bf16) 모델의 값이 아니다. 파일의 양자화 손실은 따로다
   (비교의 '다른 모델로 점수'가 그것을 재는 길).
4. 지원하는 구조는 qwen2 · qwen3(GGUF)뿐이다. 다른 구조는 모델 다양성 단계에서.
5. 다른 엔진과는 기록으로만 잰다. 화면의 글은 사실(계약 · CPU 참조 · 교차 제조사)만 적고 다른 제품을 깎지 않는다.
6. **받을 것**(사용자 허락이 필요):
   - lm-evaluation-harness(pip — 따로 둔 venv)
   - 평가 데이터(Hugging Face: ai2_arc · gsm8k — 수 MB)
   - llama.cpp 의 그날의 최신 공식 CUDA zip(약 150 MB — 기록용)
   - 모델은 이미 이 PC 에 있다.
7. GPU 시간(어림): 모델 불러오기(넷 × 두 백엔드), 판정 시험 · lm-evaluation-harness(두 배치 × 두 백엔드), R1 교차검증(약 15 분),
   비용 측정 — 세 ~ 네 시간.
8. 사용자가 계획과 받기를 확인했다(2026-10-15 — "그 계획대로 진행해, 다운로드도 허락할게"). 첫 초안(지문 · 다시 돌리기 · 배치 보기
   중심)은 사용자의 물음("실제 연구자에게 도움이 되는 정보인가?")에 답하며 버리고 이 판으로 다시 썼다. 이 문서를 커밋한 뒤에 구현 · 측정한다.
