# 21단계 — 7B 의 행렬곱: 자리 둘 계약의 두 배 텐서 일이 드러나는가 (2026-10-11)

제3자 평가(2026-10-10)는 "큰 모델로 갈수록 불리한 구조적 요인"을 짚었다. 자리 둘 계약은 활성값을 두 자리로 나눠 정수 텐서 곱을 두 번 한다.
그래서 계산이 지배하는 긴 프롬프트에서는 상한이 8 비트 엔진의 절반이다. 평가는 "Qwen 7B~8B 의 Q8_0 에서 프롬프트 2K~8K 를 재면 그 비용이
드러나는지 알 수 있다"고 했다. 이 비용은 GeulPU 스스로도 적어 둔 것이다(docs/17 의 10단계 — "같은 효율이면 8 비트 · FP8 엔진보다 두 배 느린
것이 '적힌 대로만 잃는다'의 값").

사용자 결정(2026-10-11):
- "측정 진행해봐" — 7B 모델(Qwen2.5-7B-Instruct, 공식 GGUF Q8_0)을 허락받아 내려받았다.
- 범위: 행렬곱을 먼저 잰다(이 단계). 머리 크기 128 의 어텐션까지 넣은 7B 전체는 22단계에서 한다.

7B 프롬프트의 연산은 대부분 행렬곱이다. 셈으로 행렬곱 1.07 × 10¹⁴, 어텐션 1.35 × 10¹³ 이라, 프롬프트 8192 에서 어텐션은 약 1할이고 2048 에서는
3% 쯤이다. 판정 기준을 결과보다 먼저 적는다.

## 무엇을 재나

- **모델**: Qwen2.5-7B-Instruct 공식 GGUF Q8_0.
  - 세 조각(SHA-256 26e30cb4… · e93856ce… · 8f29c0e4…)을 이 PC 의 llama-gguf-split 으로 합쳤다(8,098,525,184 B, 텐서 339 개).
  - 크기: 너비 3584 · 머리 28(머리 크기 128) · KV 머리 4 · 층 28 · 확장폭 18944 · 낱말 152064. 저장소에는 넣지 않는다.
- **행렬곱** — 층 0 의 실제 가중치로 잰다.
  - **글**: 정수 타일 판(18단계 엔진과 같은 모듈 `qwen2Q8.gl` 의 판 — K · N 은 띄울 때 받는다)으로 넷.
    - qkv: 3584 → 4608, 끝손질 없음.
    - o: 3584 → 3584, 잔차.
    - gate·up: 3584 → 2 × 18944, SwiGLU 정수 끝손질 — down 의 자리 둘을 바로 낸다.
    - down: 18944 → 3584, 잔차.
    - 판은 엔진과 같은 재기로 행 수마다 고른다.
  - **llama.cpp** b11496: 같은 텐서를 `ggml_mul_mat`(CUDA, Q8_0)으로 일곱 번 — q · k · v · o · gate · up · down. 활성값을 8 비트로 다시
    양자화하고 int8 텐서 코어로 곱한다(MMQ).
- **행 수**: 512 · 2048 · 8192.
- **시간**: 18e 와 같은 방법이다.
  - 프로세스(글 도구, llama.cpp 도구)를 번갈아 셋씩 돌린다.
  - 프로세스마다 데운 뒤 일곱 번 × 세 묶음을 재서, 묶음마다의 중앙값의 중앙값을 쓴다.
  - 층 하나의 시간 = 그 층의 행렬곱 시간의 합.
- **llama.cpp 의 행 수**: llama.cpp 는 프롬프트를 n_ubatch(기본 512)씩 넣는다. 그래서 프롬프트 n 의 행렬곱은 (행 512 의 시간) × n / 512 이다.
  행 n 을 한 번에 넣은 시간도 재서 둘 중 빠른 쪽을 쓴다(llama.cpp 에 유리하게).
- **효율**: int8 최고치 320 TOPS 대비. 글은 자리 둘(곱 두 번)로, llama.cpp 는 한 번으로 센다.

- llama-bench 로 잰 7B 전체의 프롬프트(2048 · 8192)와 생성 시간 — 행렬곱의 몫을 가늠한다
- 22단계(7B 전체)를 위한 바닥 — 행렬곱만의 시간 × 28 층

### 미리 밝혀 둘 것

1. **층 하나(0), 행렬곱만이다.** 어텐션(머리 128)과 그 앞뒤의 커널은 22단계다.
2. **글의 qkv 는 끝손질 없이 잰다.** 머리 128 의 RoPE + KV 끝손질은 아직 없다(22단계에서 만든다). 0.5B 엔진에서 qkv 는 RoPE + KV 끝손질과
   함께 돈다.
3. **끝손질의 차이.** 글은 잔차 · SwiGLU · 다음 행렬곱의 자리 둘을 행렬곱 안에서 한다. llama.cpp 는 잔차 · SwiGLU 를 따로 커널로 하는데, 이
   비교에는 그 커널들을 넣지 않는다(글 쪽에 불리하다). 들어가는 활성값의 바꾸기는 쪽마다 다르다:
   - llama.cpp 는 `ggml_mul_mat` 안에서 8 비트로 다시 양자화하므로 그 시간이 잰 값에 든다.
   - 글은 qkv · o 의 입력 자리 둘을 앞 커널(RMS 정규화 · 어텐션)이 내므로 그 시간이 잰 값에 들지 않는다(글 쪽에 유리하다).
   - down 의 입력은 두 쪽 모두 든다(글은 gate·up 의 끝손질, llama.cpp 는 down 의 다시 양자화).
4. **Q4 는 재지 않는다.** 7B 는 Q8_0 만 내려받았다.
5. **대조 도구는 파이썬이다.** CPU 참조와 llama.cpp 를 부르는 ggml C API 쪽이 그렇다. 글 쪽 재기는 글(geul) 언어 도구다.
