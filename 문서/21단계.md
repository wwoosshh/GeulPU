# 21단계 — 7B 의 행렬곱: 자리 둘 계약의 두 배 텐서 일이 드러나는가 (2026-10-11)

제3자 평가(2026-10-10)는 "큰 모델로 갈수록 불리한 구조적 요인"을 짚었다. 자리 둘 계약은 활성값을 두 자리로 나눠 정수 텐서 곱을 두 번 한다.
그래서 계산이 지배하는 긴 프롬프트에서는 상한이 8 비트 엔진의 절반이다. 평가는 "Qwen 7B~8B 의 Q8_0 에서 프롬프트 2K~8K 를 재면 그 비용이
드러나는지 알 수 있다"고 했다. 이 비용은 GeulPU 스스로도 적어 둔 것이다(docs/17 의 10단계 — "같은 효율이면 8 비트 · FP8 엔진보다 두 배 느린
것이 '적힌 대로만 잃는다'의 값").

사용자 결정(2026-10-11):
- "측정 진행해봐" — 7B 모델(Qwen2.5-7B-Instruct, 공식 GGUF Q8_0)을 허락받아 내려받았다.
- 범위: 행렬곱을 먼저 잰다(이 단계). 머리 크기 128 의 어텐션까지 넣은 7B 전체는 22단계에서 한다.

7B 프롬프트의 연산은 대부분 행렬곱이다. 셈으로 행렬곱 1.07 × 10¹⁴, 어텐션 1.35 × 10¹³ 이라, 프롬프트 8192 에서 어텐션은 약 1할이고 2048 에서는
3% 쯤이다. 판정 기준을 결과보다 먼저 적는다.

## 무엇을 재나

- **모델**: Qwen2.5-7B-Instruct 공식 GGUF Q8_0.
  - 세 조각(SHA-256 26e30cb4… · e93856ce… · 8f29c0e4…)을 이 PC 의 llama-gguf-split 으로 합쳤다(8,098,525,184 B, 텐서 339 개).
  - 크기: 너비 3584 · 머리 28(머리 크기 128) · KV 머리 4 · 층 28 · 확장폭 18944 · 낱말 152064. 저장소에는 넣지 않는다.
- **행렬곱** — 층 0 의 실제 가중치로 잰다.
  - **글**: 정수 타일 판(18단계 엔진과 같은 모듈 `qwen2Q8.gl` 의 판 — K · N 은 띄울 때 받는다)으로 넷.
    - qkv: 3584 → 4608, 끝손질 없음.
    - o: 3584 → 3584, 잔차.
    - gate·up: 3584 → 2 × 18944, SwiGLU 정수 끝손질 — down 의 자리 둘을 바로 낸다.
    - down: 18944 → 3584, 잔차.
    - 판은 엔진과 같은 재기로 행 수마다 고른다.
  - **llama.cpp** b11496: 같은 텐서를 `ggml_mul_mat`(CUDA, Q8_0)으로 일곱 번 — q · k · v · o · gate · up · down. 활성값을 8 비트로 다시
    양자화하고 int8 텐서 코어로 곱한다(MMQ).
- **행 수**: 512 · 2048 · 8192.
- **시간**: 18e 와 같은 방법이다.
  - 프로세스(글 도구, llama.cpp 도구)를 번갈아 셋씩 돌린다.
  - 프로세스마다 데운 뒤 일곱 번 × 세 묶음을 재서, 묶음마다의 중앙값의 중앙값을 쓴다.
  - 층 하나의 시간 = 그 층의 행렬곱 시간의 합.
- **llama.cpp 의 행 수**: llama.cpp 는 프롬프트를 n_ubatch(기본 512)씩 넣는다. 그래서 프롬프트 n 의 행렬곱은 (행 512 의 시간) × n / 512 이다.
  행 n 을 한 번에 넣은 시간도 재서 둘 중 빠른 쪽을 쓴다(llama.cpp 에 유리하게).
- **효율**: int8 최고치 320 TOPS 대비. 글은 자리 둘(곱 두 번)로, llama.cpp 는 한 번으로 센다.

## 판정 (미리 정함)

| 판정 | 기준 (미리 정함) | 상태 |
|---|---|---|
| 21a 비트 | 7B 층 0 의 네 가중치(qkv · o · gate·up · down)로, 글의 정수 타일 판 11 개 모두의 출력(끝손질 없음, 행 64, 무작위 활성값 — 블록마다 크기가 다르게)이 CPU 참조(`계약/정수계약.행렬곱`, 자리 둘)와 비트까지 같다 | |
| 21b 속도 | 프롬프트 2048 · 8192 에서 층 하나의 행렬곱 시간의 비 r = 글 / llama.cpp 로 칸을 적는다(통과 · 미달이 아니라 어느 칸인지). r ≤ 1 이면 "두 배의 텐서 일이 7B 에서도 드러나지 않는다(글이 빠르다)", 1 < r < 2 이면 "드러나지만 두 배는 아니다", r ≥ 2 이면 "그대로 드러난다". 행 512 는 기록 | |

판정이 아닌 기록:
- 행렬곱마다의 시간 · 고른 판 · 효율
- llama-bench 로 잰 7B 전체의 프롬프트(2048 · 8192)와 생성 시간 — 행렬곱의 몫을 가늠한다
- 22단계(7B 전체)를 위한 바닥 — 행렬곱만의 시간 × 28 층

### 미리 밝혀 둘 것

1. **층 하나(0), 행렬곱만이다.** 어텐션(머리 128)과 그 앞뒤의 커널은 22단계다.
2. **글의 qkv 는 끝손질 없이 잰다.** 머리 128 의 RoPE + KV 끝손질은 아직 없다(22단계에서 만든다). 0.5B 엔진에서 qkv 는 RoPE + KV 끝손질과
   함께 돈다.
3. **끝손질의 차이.** 글은 잔차 · SwiGLU · 다음 행렬곱의 자리 둘을 행렬곱 안에서 한다. llama.cpp 는 잔차 · SwiGLU 를 따로 커널로 하는데, 이
   비교에는 그 커널들을 넣지 않는다(글 쪽에 불리하다). 들어가는 활성값의 바꾸기는 쪽마다 다르다:
   - llama.cpp 는 `ggml_mul_mat` 안에서 8 비트로 다시 양자화하므로 그 시간이 잰 값에 든다.
   - 글은 qkv · o 의 입력 자리 둘을 앞 커널(RMS 정규화 · 어텐션)이 내므로 그 시간이 잰 값에 들지 않는다(글 쪽에 유리하다).
   - down 의 입력은 두 쪽 모두 든다(글은 gate·up 의 끝손질, llama.cpp 는 down 의 다시 양자화).
4. **Q4 는 재지 않는다.** 7B 는 Q8_0 만 내려받았다.
5. **대조 도구는 파이썬이다.** CPU 참조와 llama.cpp 를 부르는 ggml C API 쪽이 그렇다. 글 쪽 재기는 글(geul) 언어 도구다.

## 결과 (2026-10-11)

**21a 통과. 21b 는 두 칸 모두 "드러나지만 두 배는 아니다"** — 프롬프트 2048 에서 r = 1.20, 8192 에서 r = 1.77.
- 글은 같은 행렬곱을 두 자리로 두 번 한다. 대신 int8 최고치의 55~58% 를 쓴다(llama.cpp 는 33~35%). 그래서 두 배의 일 가운데 대부분을 타일
  효율로 메워, 2048 에서는 llama.cpp 의 1.2 배다.
- 8192 에서 더 벌어진 것은 계약 때문이 아니다. 판의 블록 차례가 L2 를 넘는 두 피연산자를 다루지 못해서다(아래 분석). 이것은 고칠 수 있다.

| 21a 비트 | **통과**. 7B 층 0 의 네 가중치(qkv 3584 → 4608 · o 3584 → 3584 · gate·up 3584 → 37888 · down 18944 → 3584)로, 정수 타일 판 11 개의 출력이 서로 비트까지 같고(판 0 과 다른 판 0 개), 판 0 의 출력이 CPU 참조와 다른 칸 0 이다(행 64, 칸 294,912 · 229,376 · 2,424,832 · 229,376) |

### 8192 에서 왜 벌어졌나 — 판의 블록 차례와 L2

글의 효율이 2048 의 58% 에서 8192 의 38% 로 떨어졌다. 떨어진 것은 qkv(행 4 배에 시간 10 배)와 gate·up(6.8 배)뿐이다. o 와 down 은 행 수만큼
늘었다. 8192 행에서는 활성값의 자리 둘이 59 MB(K = 3584)로 L2(48 MB)를 넘는다.
- 판의 블록 차례는 둘이다. 행먼저는 가중치를 L2 에 두고 활성값을 열 조각마다 다시 읽는다. 열먼저는 활성값을 두고 가중치를 행 조각마다 다시
  읽는다.
- qkv 는 끝손질 없는 판으로 쟀는데, 그 판에는 열먼저가 없다. 그래서 59 MB 의 활성값을 열 조각마다(고른 판 6 — 열 256 개씩 — 에서 18 번) 다시 읽는다.
- gate·up 은 가중치(136 MB)도 L2 를 넘어, 어느 차례로도 한쪽을 다시 읽는다.
- llama.cpp 는 프롬프트를 512 행씩 넣으므로(n_ubatch) 활성값이 늘 L2 에 든다.

글의 결과는 행을 어떻게 나눠 넣어도 비트가 같다(20a). 그래서 8192 를 2048 씩 넷으로 넣을 수 있다. 그렇게 셈하면 4 × 10.318 = 41.27 ms,
r = 1.16 이다(셈일 뿐 판정이 아니다). 남은 일은 블록 차례를 묶음으로 돌리는 판(그룹 래스터) 또는 덩이 나누기다 — 22단계에서.

### 판정이 아닌 기록

- **7B 전체**(llama-bench, 기본 설정 — n_ubatch 512):
  - 프롬프트 2048: 6,767 t/s(302.6 ms)
  - 프롬프트 8192: 6,156 t/s(1,330.8 ms)
  - 생성: 59.29 t/s(16.87 ms/토큰)

  n_ubatch 2048 로는 6,486 · 6,043 t/s 로 더 느리다.
- **행렬곱의 몫**: llama.cpp 의 프롬프트 시간 가운데 행렬곱(층 하나 × 28)은 2048 에서 241.5 / 302.6 ms(80%), 8192 에서 998 / 1,331 ms(75%)다.
  글의 행렬곱만 × 28 은 2048 에서 288.9 ms, 8192 에서 1,769 ms(2048 씩 넣으면 1,156 ms)다. 7B 전체(22단계)는 여기에 어텐션 등이 더해진다.
- **생성은 대역폭이 정한다**: 토큰마다 약 7.5 GB 를 읽는다(낱말표를 뺀 가중치). 13단계에서 잰 실측 대역폭 460 GB/s 로 바닥은 약 16.3 ms 다.
  llama.cpp 의 16.87 ms 는 바닥의 1.04 배다. 생성에서는 계약의 두 배 일이 거의 드러나지 않을 자리다(행이 하나라 계산이 아니라 읽기가 정한다).
- **고른 판**(qkv · o · gate·up · down — 후보 번호, 11 이상은 열먼저):
  - 2048: 10 · 21 · 0 · 19(셋 다 같음)
  - 8192: 6 · 19/21/11 · 21 · 18/19

### 밝혀 둘 것

1. **시운전에서 도구의 버그를 찾아 고쳤다.** 공식 실행 전의 시운전(비트)에서 down(K = 18944)만 CPU 참조와 칸의 59% 가 달랐다. 원인은
   글 도구였다. 비트 모드에서 down 의 입력 자리 둘을 K = 3584 크기로 잡은 버퍼(자릿값 · 정보)에 바꿔 넣어 넘쳐 썼다. F 크기 버퍼(자릿값2 ·
   정보2)로 고친 뒤 넷 모두 다른 칸 0 이었다. 공식 실행은 고친 도구(b1c509c3…)로 했다. 재기 모드는 처음부터 F 크기 버퍼를 썼다.
2. **qkv 는 끝손질 없는 판으로 쟀다**(미리 밝혀 둔 2). 그 판에는 열먼저가 없어 8192 에서 불리하다(위 분석). 0.5B 엔진의 qkv 끝손질
   (RoPE + KV)에는 열먼저가 있다.
3. **llama.cpp 의 시간은 그래프 계산(동기) 한 번의 벽시계다.** 행렬곱마다 따로 잰 합(512: 2.232 ms)과 한 그래프(2.228 ms)가 거의 같아, 부를 때의
   몫은 작다.
4. 결과 파일은 [결과/21단계/](결과/21단계/)에 있다: 21a 비트, 프로세스마다의 글 · llama.cpp 기록, 요약, llama-bench 표, 실행 기록.
