# 25단계 — 층 나누기: 여러 GPU 에 모델을 나눠 싣기 (2026-10-11)

사용자 방향(23 · 24단계에 적은 것): 실제로 쓰는 사람들은 VRAM 50 ~ 100 GB 의 작은 서버급, 그리고 대형 서버에서 32B · 72B · 120B 를 돌린다.
추천 순서의 (3)이 이 단계다 — 한 GPU 에 들지 않는 모델을 층으로 나눠 여러 GPU 에 싣는다. **이 PC 에는 GPU 가 한 장뿐이다.** 그래서 한 GPU
안에서 여러 장을 흉내 낸다: 조각마다 CUDA 문맥을 따로 만들고(메모리 · 모듈 · 그래프가 따로), 조각 사이의 넘김은 실제 여러 GPU 에서 쓰는
피어 복사(`cuMemcpyPeer`)로 한다. 같은 코드가 장치 번호만 바꾸면 여러 GPU 에서 돈다.

판정 기준을 결과보다 먼저 적는다.

## 무엇을 만드나

1. **엔진의 층 범위**: 엔진 하나(조각)가 층 [시작, 끝)만 싣는다 — 그 층의 가중치 · KV 캐시만. 첫 조각은 임베딩, 끝 조각은 마지막 RMS · 로짓 ·
   가장 큰 번호를 맡는다. 조각 사이로는 잔차 흐름(행 × 너비 짧은실수)만 넘긴다.
2. **조각 여럿(호스트, 글)**: 조각마다 문맥(장치 번호를 받는다 — 이 PC 에서는 모두 0) · 모듈 · 판 고르기 · 그래프. 프롬프트 덩이는 조각 0 →
   1 → … 차례로, 생성은 토큰마다 조각의 그래프를 차례로 띄우고 잔차 · 다음 토큰 · 걸음을 넘긴다. 나누는 자리는 장치마다의 메모리 예산에 맞춰
   층의 바이트로 고른다(예산은 장치의 남은 메모리, 흉내 낼 때는 주는 값 — "12 GB 를 6 GB 둘처럼").
3. **실행기 · 시험 · 재기 도구**: `--나누기 P`(장치 0 에 P 조각 — 흉내) · `--장치 0,1,…` · `--예산 GB` 를 받는다.

판정이 아닌 기록: 조각마다의 층 수 · 장치 메모리, 넘김 한 번의 시간(잔차 복사 · 문맥 바꾸기), llama.cpp 의 층 나누기(`--split-mode layer`)와의
견주기는 이 PC 에 GPU 가 한 장이라 하지 않는다.

### 미리 밝혀 둘 것

1. **이 PC 의 결과는 흉내다.** 조각들이 한 GPU 를 나눠 쓰므로 메모리는 물리적으로 합쳐 12 GB 이고(예산으로 나눠 센다), 피어 복사는 같은 장치 안의
   복사다. 실제 여러 GPU 의 넘김은 PCIe · NVLink 를 지나 더 오래 걸린다 — 25c 는 소프트웨어 쪽의 값(동기화 · 복사 · 띄움)을 잰다.
2. **32B · 72B 의 실제 모델은 이 단계에서도 돌리지 않는다**(합친 메모리가 12 GB). 층 나누기의 길(비트)은 합성 72B 와 실제 7B · 14B 로 본다.
3. **처음 판은 조각을 차례로 돌린다**(한 흐름의 생성에서 층 나누기는 원래 차례다). 여러 요청을 겹쳐 돌리는 파이프라인은 (4)의 서버 기능에서.
4. **대조 도구는 파이썬이다**(대조 · 모음). 엔진 · 실행기 · 시험 · 재기 도구는 글이다.

## 공식 실행 전에 덧붙임 — 구현 중에 바뀐 것 (판정 기준은 그대로)

개발 판에서 잰 것도 결과보다 먼저 밝힌다(판정은 공식 실행의 값으로 한다).

1. **넘김을 비동기로 바꿨다 — 미리 적은 "피어 복사(`cuMemcpyPeer`)" 와 다르다.** 처음 판은 조각마다 호스트가 기다리고 `cuMemcpyPeer`(동기)로
   넘겼다. 같은 장치의 문맥 둘 사이에는 피어 접근이 없어(`cuCtxEnablePeerAccess` → 217) 드라이버가 호스트 메모리를 지나 복사하는데, 이것이
   호스트를 막는다 — 잔차 14 KB + 토큰 8 B 의 한 바퀴가 동기 ~170 µs, `cuMemcpyPeerAsync`(비동기)로도 ~140 ~ 170 µs 동안 호스트가 막힌다
   (`재기/넘김재기25.py`). 그래서 경계마다 길을 고른다 — (가) 장치가 다르고 피어 접근이 되면(`cuDeviceCanAccessPeer` · `cuCtxEnablePeerAccess`)
   `cuMemcpyPeerAsync`, (나) 아니면 모든 문맥에서 고정된 호스트 칸(`cuMemHostAlloc` PORTABLE)을 지나 비동기로: 보내는 조각의 흐름에
   내림(`cuMemcpyDtoHAsync`) · 사건, 받는 조각의 흐름이 그 사건을 GPU 쪽에서 기다리고(`cuStreamWaitEvent`) 올림(`cuMemcpyHtoDAsync`) — 한 바퀴
   ~41 µs, 호스트를 막지 않는다. 생성의 다음 토큰(끝조각 → 조각 0)과 걸음(호스트 → 끝조각이 아닌 조각)도 고정 칸을 지나 비동기로 넘긴다.
   이 PC 에서는 모든 경계가 (나)다. (가)의 복사는 `--넘김 피어` 로 이 PC 에서도 돈다(드라이버가 호스트를 지나 느리지만 비트를 본다). 장치가
   다른 피어 길(피어 접근 켜기)은 이 PC 에서 돌려 보지 못했다.
2. **조각 0 은 끝조각의 앞 일 뒤에 시작한다** — 미리 밝힌 3("차례로")과 같은 뜻. 처음 판은 덩이를 띄우고 끝조각을 기다리지 않아 다음 덩이의
   조각 0 이 앞 덩이의 끝조각과 한 GPU 에서 겹쳤다. 문맥이 다른 일은 GPU 가 시간을 나눠 돌리므로 겹치면 느려진다 — 개발 판 7B Q4_0 두 조각의
   프롬프트 2048 · 8192 가 421.2 · 2368.8 ms(한 조각 355.5 · 1773.8 ms). 사건으로 이은 뒤 355.9 · 1772.1 ms.
3. **한 GPU 에서 문맥 둘을 번갈아 돌리는 값이 크다 — 흉내의 값.** 4.5 ms 커널 둘을 '토큰' 하나로: 문맥 하나에서 잇달아 9.004 ms, 문맥 둘에
   하나씩(사건으로 이음) 9.25 ms — GPU 쪽 문맥 바꾸기가 한 번에 ~120 µs 다(`재기/문맥바꾸기25.py` — 파이썬 ctypes 탐침, 엔진과 따로). 실제 여러
   GPU 에서는 장치마다 문맥 하나가 제 일만 하므로 이 값이 없다. 개발 판에서 7B Q4_0 두 조각(조각마다 문맥)의 생성은 9.436 · 9.706 · 10.646
   ms/토큰으로 23단계 공식 한 조각(9.138 · 9.392 · 10.297)의 1.033 · 1.033 · 1.034 배였다 — 대부분이 토큰마다의 문맥 바꾸기 둘이다. 그래서
   **같은 장치의 조각이 앞 조각의 문맥을 함께 쓰는 판(`--문맥 하나` — 모듈 · 메모리 · 그래프는 조각마다 따로, 넘김은 문맥 안 복사)을 기록으로
   함께 잰다**(개발 판 9.149 · 9.416 · 10.333 — 1.001 · 1.003 · 1.003 배). 25c 판정은 미리 정한 대로 조각마다 문맥으로 한다.
4. **25c 를 재는 법(공식 실행 전에 정함)**: 모델(7B Q4_0 · 14B Q4_0)마다 한 조각 · 두 조각(조각마다 문맥) · 두 조각(문맥 하나)을 번갈아 세
   번(한 번 = `재기_7B` — 칸마다 일곱 번의 중앙값을 세 묶음, 그 가운데), 칸마다 세 번의 가운데 값으로 비를 낸다(`재기/모음25.py`). 세 조각 ·
   네 조각(7B), 세 조각(14B)은 한 번씩(기록). GPU 일은 하나씩 차례로.
5. **25b 의 길**: `--예산 6` 만 주면(조각 하나) "조각 0 이 예산 … 를 넘는다 — 조각이 더 든다" 를 알리고 멈춘다. `--나누기 2 --예산 6` 이면 예산
   안에서 앞부터 채워 나누는 자리를 고른다.
6. **실행기**: `--나누기` · `--예산` · `--장치` · `--넘김` · `--문맥` 을 받는다 — 이때는 올림을 일꾼 스레드로 겹치지 않고 차례로 한다. 기록으로
   7B Q4_0 의 채팅 두 질문을 한 조각 · 두 조각으로 돌려 답을 견준다.
7. 25a 의 한 조각 요약은 이 실행에서 다시 낸 것(같은 커밋)과 앞 단계의 요약(23b · 24c) 둘 다와 견준다. 기록으로 7B Q4_0 두 조각의
   `--문맥 하나` · `--넘김 피어` 도 다섯 길을 본다. 개발 판에서는 25a 의 모든 경우(7B Q4_0 의 P 2 · 3 · 4, 14B Q4_0 의 P 2(예산) · 3, 합성
   72B 의 P 2 · 4, 문맥 하나 · 피어)가 한 조각의 요약과 바이트까지 같았다.

### 실행 뒤에 밝혀 둘 것

1. **14B 두 조각의 25c 는 메모리 때문에 재지 못했다.** 흉내에서는 조각마다의 일 버퍼(로짓칸 · 시험칸 · 자리 버퍼 등)와 모듈, 둘째 쿠다 문맥이 한
   장에 함께 오른다. 실제 여러 GPU 에서는 장치마다 따로라 이 문제가 없다. 흉내에 맞춰 버퍼를 줄이는 일은 하지 않았다(흉내에 맞춘 최적화가 될
   수 있어서).
2. **조각마다 문맥의 값에는 흉내의 문맥 바꾸기가 들어 있다**(위 기록). 반대로 실제 여러 GPU 의 PCIe · NVLink 전송은 이 PC 에서 재지 못한다 —
   생성의 넘김은 토큰마다 14 KB(7B)라 작고, 프롬프트는 덩이(1024 행)마다 14.7 MB(7B)다.
3. 장치가 다른 조각의 피어 길(`cuDeviceCanAccessPeer` · `cuCtxEnablePeerAccess`)은 돌려 보지 못했다(미리 적은 대로).
