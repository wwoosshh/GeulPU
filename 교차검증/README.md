# 교차 검증 — 다른 PC 에서도 같은 출력이 나오는가

GeulPU 는 계산을 정확한 정수 계약으로 해서, 같은 입력이면 어디서 어떻게 계산해도 같은 비트를 낸다고 주장한다. 이 폴더는 그 주장을
**다른 PC** 에서 확인하는 스크립트다.

## 실행
git 이 있는 윈도 PC 에서:
```
git clone https://github.com/wwoosshh/GeulPU
GeulPU\교차검증\run.bat
```
`run.bat` 이 차례로 한다.
1. 환경 검사 — 운영체제(판 · 빌드), 모든 GPU 의 이름 · 연산 능력 · VRAM · 드라이버와 그 방식 · VBIOS · PCIe · 최대 클럭 · 전력 한도,
   nvcuda.dll 판 · CUDA 판, CPU · RAM, 디스크, 하드웨어 가속 GPU 일정, 전원 계획, git, GeulPU 커밋. 실패가 있으면 여기서 멈춘다.
2. 소스에서 빌드(1~3 분) — 글 1.3.1 공개 배포판의 컴파일러로 글 저장소의 고정 커밋(`시험/글저장소커밋.txt`, CI 와 같다)의 글 컴파일러를
   두 번 빌드하고(고정점), PTX 뒷단 → 서버 → 커널 생성기 → 7B Q8_0 모듈 → PTX. 단계마다 기준 PC 에서 만든 것과 SHA-256 을 대조한다.
3. 모델 받기 — DeepSeek-R1-Distill-Qwen-7B Q8_0 (8.1 GB, Hugging Face `unsloth/DeepSeek-R1-Distill-Qwen-7B-GGUF`).
   `교차검증\` 에 미리 넣어 두면 받지 않는다.
4. 생성 — 서버를 127.0.0.1 에서만 띄우고, 수학 문제 32 개를 탐욕 생성(temperature 0, 상한 3200 토큰)으로. 걸음마다의 로짓 해시도 받는다.
5. 비교 — 기준 PC 의 출력(`expected.json`)과 글자 하나까지.
6. 자기 진단(32단계, 1 분 안팎) — `diag.json` · `diag.json.txt` 에 적는다.
   - 이 기기의 바닥(메모리 읽기 대역 · 정수 텐서 코어 최고치)을 그 자리에서 잰다.
   - 7B 엔진의 커널 종류마다 시간과 바닥 대비를 적는다: 생성 한 줄 · 여덟 줄 · 프롬프트, 서버의 생성 걸음(슬롯 여덟 · 넷).
   - 엔진이 이 기기에서 후보마다 잰 판과 고른 판을 적는다.
   - 31단계의 후보로 고른 그래프와 모든 후보로 고른 그래프를 번갈아 잰 비(슬롯 여덟 · 넷)를 적는다.
   - 같은 자리에서 여러 번 재 가장 빠른 값을 쓰고, 그때 GPU 를 쓰던 다른 프로그램을 함께 적는다(`diag-gpu-state.txt`).
7. `교차검증\result-….zip` — 환경 · 빌드 해시 · 출력 · 비교 · 진단 · 기록. 사용자 이름 · 컴퓨터 이름 · GPU 고유번호는 넣지 않고 경로는 지운다.

**진단만**: `GeulPU\교차검증\diag.bat` — 빌드 · 모델 확인 뒤 생성은 건너뛰고 6 만 한다(모델이 이미 있으면 몇 분). 결과 zip 을 보내 주면 된다.

필요: 윈도 10/11 64 비트, git, NVIDIA RTX 30 시리즈 이상(VRAM 12 GB 이상 권장 — 10 GB 는 슬롯을 줄여 느리게), 디스크 여유 10 GB.
파이썬은 필요 없다(글 1.3.1 로 컴파일러를 빌드하지 못할 때만 대신 쓴다).

## 실행 — AMD 등 (Vulkan, 34단계)
GeulPU 는 nvcuda.dll 없이 vulkan-1.dll 로도 돈다. 같은 커널 소스를 글(geul) 컴파일러의 SPIR-V 뒷단이 낸다
([31단계](../문서/31단계.md) · [34단계](../문서/34단계.md)). 같은 실험을 AMD 등의 Vulkan GPU 에서:
```
git clone https://github.com/wwoosshh/GeulPU
GeulPU\교차검증\runV.bat
```
`runV.bat` 은 `run.bat` 과 같은 차례로 돈다. 모델 · 문제 · 설정 · 비교 기준(`expected.json` — 기준 PC 의 CUDA 출력)도 같다. 다른 곳:
1. 환경 검사 — nvidia-smi 대신 윈도의 그래픽 장치 목록(이름 · 회사 · 드라이버 판 · 날짜)과 Vulkan 로더(vulkan-1.dll).
2. 빌드 — 글 컴파일러 다음에 **Vulkan 장치 검사**를 한다(`호스트/장치V.gl`).
   - 모든 Vulkan 장치의 속성 · 기능 · 확장 · 협력 행렬 모양 · 비정규수 버림 모드 · 할당 한도 · 메모리 힙 · 드라이버를 `vulkan-devices.json` 에 적는다.
   - 엔진이 고르는 장치(첫 외장 GPU)에 GeulPU 가 쓰는 것이 있는지 본다: 서브그룹 크기 32 · 공유 메모리 48 KB · 64/16/8 비트 정수 ·
     장치 주소 · 정수 내적 · 공유 메모리 명시 배치 등. 없으면 여기서 멈추고 결과 zip 을 남긴다.
   - 그다음 SPIR-V 뒷단 → 서버(Vulkan) → 커널 생성기 → 7B Q8_0 모듈 둘 → SPIR-V 묶음. 해시는 `expected.json` 의 `build` · `build_vulkan` 과 대조한다.
4. 생성 — 모듈마다 한 번(127.0.0.1 에서만).
   - 협력 행렬 모듈: 장치에 정수 협력 행렬(VK_KHR_cooperative_matrix, 부호 있는 8 비트 → 32 비트)이 있을 때. 모양은 장치가 받는 것
     (AMD RDNA3 16x16x16 · NVIDIA 16x16x32). 정수 곱의 합은 정확해서 모양이 달라도 같은 비트다.
   - 기본 모듈: 텐서곱을 서브그룹 셔플 · 정수 내적으로 흉내 낸다. 느리지만 모든 장치에서 돈다.
5. 비교 — 모듈마다 32 문제를 기준(CUDA)과 글자 하나까지.
6. 자기 진단 — `호스트/진단V.gl`. 정수 텐서의 최고치는 협력 행렬이 있으면 그것으로 잰다. Vulkan 은 메모리 클럭 · 버스를 알려 주지 않아
   사양 대역은 비워 둔다.
7. `교차검증\result-V-….zip`.

**진단만**: `GeulPU\교차검증\diagV.bat`.

필요: 윈도 10/11 64 비트, git, Vulkan 1.3 드라이버(AMD 는 Adrenalin 최신), VRAM 12 GB 이상 권장, 디스크 여유 10 GB. AMD 는 서브그룹
크기 32 를 고를 수 있는 RDNA(RX 5000 이후)여야 한다. GCN(RX 400 · 500 · Vega)은 64 뿐이라 장치 검사에서 멈춘다.

- 기준 PC 의 Vulkan(2026-10-14, RTX 4070 Ti): 협력 16x16x32 모듈 · 기본 모듈 모두 32/32 가 CUDA 기준과 같다. 82,673 걸음의 로짓
  해시도 모두 같다. 생성(슬롯 8) 4.8 · 4.9 분, VRAM 최고 9.9 GB.
- AMD 에서는 아직 돌려 보지 않았다. 16x16x16(RDNA3) 협력 모양은 NVIDIA 가 받지 않아 이 PC 에서 확인하지 못했다. 그래서 기본 모듈로도
  한 번 더 돈다.
- 첫 AMD 보고(2026-10-14, RX 9060 XT · 드라이버 26.8.1)는 장치 검사에서 멈췄다. AMD 의 윈도 드라이버는 작업 그룹의 공유 메모리를
  32 KB, 한 번의 할당을 2 GiB 로 알린다(7B 커널은 48 KB 까지, 엔진은 gate·up 가중치 4.04 GB 를 한 덩이로 썼다). 그래서 공유32 판
  (`커널생성 … --공유32` — 생성 줄 판 · 어텐션을 32 KB 안으로, 표 걸음의 RoPE 판의 매개변수를 열셋으로)을 만들고, 엔진이 한도를 넘는
  가중치를 층마다 따로 잡게 했다. 셈의 차례는 그대로라 출력은 같다 — 이 PC 에서 AMD 의 한도를 흉내 내어(`GEULPU_VULKAN_SHARED=32768`
  · `_PUSH=128` · `_ALLOC=2147483648`) 7B Q8_0 · Q4_0 다섯 길이 23b 기록과 바이트까지 같았다. `runV.bat` 은 장치에 맞춰 판을 고른다.
- 결과 zip 의 대조: `python -X utf8 -I 교차검증/대조.py <result-V-….zip>` — 모듈마다 따로 견준다.

## 실험
- 문제: 정답을 코드로 계산한 수학 문제 32 개(`requests.json` — 씨앗 31 로 만든 합성 문제, 표준 벤치마크가 아니다). 프롬프트는 모든 PC 에
  같은 토큰열(BOS + llama-server 의 대화 틀).
- 서버: `호스트/서버.gl` 에 [`토크나이저_R1.diff`](토크나이저_R1.diff) 만 더해 빌드한다(스크립트가 `work\src` 의 사본에 적용). 이 모델의
  `tokenizer.ggml.pre`(`deepseek-r1-qwen` — 바이트 BPE 의 앞자르기는 qwen2 와 같다)를 받고 끝 토큰을 `<｜end▁of▁sentence｜>` 로 둔다.
  계산(커널)은 그대로다.
- 판정(실행 전에 적음): 출력 글이 32 문제 모두 기준과 같으면 통과. 하나라도 다르면 그 GPU · 드라이버와 처음 갈린 자리를 그대로 기록한다.
  빌드 해시가 기준과 다르면 그것도 함께 기록한다(출력이 다를 때 빌드 탓인지 GPU 탓인지 가르기 위해).

### 31단계 뒤 (2026-10-14) — 빌드 해시 넷이 바뀌었다, 출력 기준은 그대로

계약의 짧은실수 규칙을 R(비정규수 버림 — [31단계](../문서/31단계.md))로 바꿨다. 그래서 `expected.json` 의 빌드 해시 여섯 중 넷이 새 값이다.
- 바뀐 것: PTX 뒷단 · 커널 생성기 · 7B 모듈 소스 · PTX
- 그대로인 것: 글 컴파일러 · 서버

출력의 기준(32 문제의 글 · 걸음마다 로짓 해시)은 그대로다. 새 빌드로 기준 PC 에서 다시 돌려 82,673 걸음이 모두 같았다. 위 두 친구 PC 의
